# AI Gateway Monitoring with OpenTelemetry

> Monitor LLM token consumption per provider and model, and the activity of Prompt Guard and the semantic cache, with KrakenD's OpenTelemetry metrics and traces.

Source: https://www.krakend.io/docs/enterprise/ai-gateway/usage-monitoring/

**AI Gateway monitoring** uses KrakenD’s [OpenTelemetry](https://www.krakend.io/docs/enterprise/telemetry/opentelemetry/) integration to report what your AI traffic consumes and how it behaves. On top of the request, latency, and error metrics KrakenD reports for every backend, the `ai/llm` component counts the input, output, and total tokens of every LLM call, tagged with the provider and the model. Use these metrics to follow the spend of each model, to compare vendors, and to detect consumption spikes in the observability stack you already have. You only need the `telemetry/opentelemetry` namespace: the AI metrics appear as soon as an exporter is configured.

## LLM Token Metrics

Every backend that uses the `ai/llm` component, either with an inline vendor block, with a reference to the [provider inventory](https://www.krakend.io/docs/enterprise/ai-gateway/provider-inventory/), or through the [AI Router](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/), reports three counters:

| OpenTelemetry metric       | Prometheus metric              | Content                              |
|----------------------------|--------------------------------|--------------------------------------|
| `krakend.llm.tokens-in`    | `krakend_llm_tokens_in_total`  | Input tokens of the prompt           |
| `krakend.llm.tokens-out`   | `krakend_llm_tokens_out_total` | Output tokens generated by the model |
| `krakend.llm.tokens-total` | `krakend_llm_tokens_total`     | Input plus output tokens             |

Each counter carries two attributes:

- `provider`: the vendor that served the request, such as `openai`, `gemini`, `anthropic`, `mistral`, `bedrock`, or `alibaba`.
- `model`: the model that served the request, such as `gpt-5-nano`.

KrakenD reads the token counts from the vendor response before the output template transforms it, so custom [prompt templates](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/#prompt-templates) do not change the metrics. With [LLM streaming](https://www.krakend.io/docs/enterprise/ai-gateway/llm-streaming/), KrakenD adds up the tokens reported in the stream and records them when the stream ends.

For example, after two calls of 30 tokens each to a `gpt-5-nano` provider, the Prometheus exporter shows:

```log
krakend_llm_tokens_in_total{model="gpt-5-nano",provider="openai"} 22
krakend_llm_tokens_out_total{model="gpt-5-nano",provider="openai"} 38
krakend_llm_tokens_total{model="gpt-5-nano",provider="openai"} 60
```

The exporter also adds the `otel_scope_*` labels it adds to every KrakenD metric, omitted here for brevity.

## LLM Traces

When you export traces, every call of the `ai/llm` component creates a `krakend-llm` span. When the call ends, the span receives the token counts as attributes, so you can see the cost of each request next to its latency:

- `krakend.llm.tokens-in`, `krakend.llm.tokens-out`, and `krakend.llm.tokens-total`: the tokens of the call.
- `provider`: the vendor that served it.

## Other AI Metrics

Other AI Gateway components report their own metrics through the same exporters:

- [Prompt Guard](https://www.krakend.io/docs/enterprise/ai-gateway/prompt-guard/#prompt-guard-metrics-and-traces) counts every guard evaluation in `krakend_promptguard_check_requests_total`, with an attribute that tells whether the request was blocked.
- The [Semantic Cache](https://www.krakend.io/docs/enterprise/ai-gateway/semantic-cache/#hit-and-miss-metrics) reports its hits and misses, which help you tune its `max_distance` and `ttl`.

## Exporting the AI Metrics

Add the `telemetry/opentelemetry` namespace to the root `extra_config` with the exporters of your observability stack. The following configuration exposes the metrics for [Prometheus](https://www.krakend.io/docs/enterprise/telemetry/prometheus/) on port `9090` and sends the traces to an OpenTelemetry collector through [OTLP](https://www.krakend.io/docs/enterprise/telemetry/opentelemetry/):

```json
{
  "$schema": "https://www.krakend.io/schema/krakend.json",
  "version": 4,
  "extra_config": {
    "telemetry/opentelemetry": {
      "service_name": "ai_gateway",
      "metric_reporting_period": 1,
      "trace_sample_rate": 1,
      "exporters": {
        "prometheus": [
          {
            "name": "local_prometheus",
            "port": 9090
          }
        ],
        "otlp": [
          {
            "name": "local_collector",
            "host": "localhost",
            "port": 4317,
            "use_http": false,
            "disable_metrics": true
          }
        ]
      }
    }
  }
}
```

The Prometheus exporter serves the metrics on `http://localhost:9090/metrics`, and the OTLP exporter only sends the traces, as `disable_metrics` is `true`. Lower `trace_sample_rate` in production to trace a fraction of the requests.

## Querying the Token Consumption

With the metrics in Prometheus, PromQL answers the usual cost questions. For instance, the tokens consumed per model in the last 24 hours:

```text
sum by (model) (increase(krakend_llm_tokens_total[24h]))
```

And the output tokens per second of each vendor, to spot a consumption spike as it happens:

```text
sum by (provider) (rate(krakend_llm_tokens_out_total[5m]))
```

Multiply these values by the price per token of each model to estimate the spend. To limit the consumption instead of observing it, see [Token Budgets](https://www.krakend.io/docs/enterprise/ai-gateway/budget-control/).
