# [AI Gateway for LLMs and AI Agents (available in KrakenD Enterprise)](https://www.krakend.io/docs/enterprise/ai-gateway/)

The **KrakenD AI Gateway** is the set of KrakenD Enterprise components that put Large Language Models (LLMs) and AI agents behind your API infrastructure. It connects your endpoints to the major LLM vendors through a single interface, chooses the model of each request, blocks malicious prompts, enforces token budgets, and reports the token consumption of every call. Use it when your applications, teams, or customers consume AI services and you need to control who uses which model, how much it costs, and what data reaches the vendors. It runs in the same binary and configuration as your API Gateway, so there is no extra product, control plane, or deployment to operate.

License requirement

The AI Gateway components require a license that includes the AI Gateway. Check the [license info](https://www.krakend.io/docs/enterprise/overview/license-file/#license-info) of your LICENSE file.

## What Is an AI Gateway?

An **AI Gateway** is an API Gateway specialized in AI workloads. It sits between the consumers and the LLM vendors, so the credentials, the model choice, and the security and cost policies live in one place instead of in every application. Consumers get a stable API, while you keep the freedom to change models and vendors behind it.

## AI Gateway Capabilities

The AI Gateway documentation follows the tasks you need to solve when you put LLMs in production. Each capability is a KrakenD component that you add to the configuration.

### Connecting to LLMs

- The [Unified LLM Interface](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/) (`ai/llm`) gives clients one request and response format for every vendor, while KrakenD builds each vendor payload with prompt templates.
- The [LLM Provider Inventory](https://www.krakend.io/docs/enterprise/ai-gateway/provider-inventory/) (`ai/providers`) declares each provider once, with its vendor, model, and credentials, so any backend references it by name.
- Built-in integrations connect to [OpenAI](https://www.krakend.io/docs/enterprise/ai-gateway/openai/), [Google Gemini](https://www.krakend.io/docs/enterprise/ai-gateway/gemini/), [Mistral](https://www.krakend.io/docs/enterprise/ai-gateway/mistral/), [Anthropic](https://www.krakend.io/docs/enterprise/ai-gateway/anthropic/), [Amazon Bedrock](https://www.krakend.io/docs/enterprise/ai-gateway/bedrock/), and [Alibaba Cloud Qwen](https://www.krakend.io/docs/enterprise/ai-gateway/alibaba/), and to [other vendors and OpenAI-compatible servers](https://www.krakend.io/docs/enterprise/ai-gateway/other-vendors/) such as Ollama.
- [LLM Streaming](https://www.krakend.io/docs/enterprise/ai-gateway/llm-streaming/) forwards the tokens as the model produces them, optionally in the OpenAI or Anthropic format whatever the vendor.

### Routing Requests to the Right Model

- The [AI Router](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/) (`ai/router`) chooses the provider of each request with header or policy gates, a classifier that picks the best model, and failover providers.
- [LLM Routing Strategies](https://www.krakend.io/docs/enterprise/ai-gateway/llm-routing/) cover the other patterns: one endpoint per provider, vendor-native passthrough, multi-LLM aggregation, and mixing LLM and non-LLM backends.

### Protecting Prompts and Data

- [Prompt Guard](https://www.krakend.io/docs/enterprise/ai-gateway/prompt-guard/) (`ai/prompt-guard`) blocks prompt injection, jailbreaks, and data exfiltration attempts with default guards, regular expressions, CEL policies, or an external classifier.
- [AI Gateway Security](https://www.krakend.io/docs/enterprise/ai-gateway/security/) isolates the consumer authentication from the vendor credentials, masks sensitive data, and prevents exfiltration.

### Controlling the Costs

- [Token Budgets](https://www.krakend.io/docs/enterprise/ai-gateway/budget-control/) cap the tokens each user, plan, or tenant consumes per hour, day, or month, with the quota component.
- The [Semantic Cache](https://www.krakend.io/docs/enterprise/ai-gateway/semantic-cache/) (`ai/semantic-cache`) returns a stored response when a new prompt means the same as a previous one, without calling the LLM.

### Observing AI Traffic

- [AI Monitoring](https://www.krakend.io/docs/enterprise/ai-gateway/usage-monitoring/) reports the input, output, and total tokens of every call per provider and model through OpenTelemetry, together with the Prompt Guard and semantic cache metrics.

### Connecting AI Agents with MCP

- The [MCP Server](https://www.krakend.io/docs/enterprise/ai-gateway/mcp-server/) (`ai/mcp`) exposes your existing APIs and services as Model Context Protocol (MCP) tools for AI agents, with authorization and per-client tool filtering.
- The [MCP Gateway](https://www.krakend.io/docs/enterprise/ai-gateway/mcp-gateway/) puts third-party MCP servers behind KrakenD to add authorization, rate limits, and observability.

## Quickstart

The following configuration declares an OpenAI provider in the inventory and exposes it on `/chat`. Replace `xxx` with your OpenAI API key, or inject it from an environment variable with [Flexible Configuration](https://www.krakend.io/docs/enterprise/configuration/flexible-config/):

```json
{
  "$schema": "https://www.krakend.io/schema/krakend.json",
  "version": 4,
  "extra_config": {
    "ai/providers": {
      "providers": [
        {
          "name": "chat",
          "provider": "openai",
          "model": "gpt-5-nano",
          "credentials": "xxx"
        }
      ]
    }
  },
  "endpoints": [
    {
      "endpoint": "/chat",
      "method": "POST",
      "backend": [
        {
          "extra_config": {
            "ai/llm": {
              "provider": "chat"
            }
          }
        }
      ]
    }
  ]
}
```

Save it as `krakend.json`, start KrakenD, and send a prompt:

Send a prompt through the AI Gateway 

```
$curl -XPOST --json '{"instructions": "Answer in one sentence", "contents": "What is an API gateway?"}' http://localhost:8080/chat
```

KrakenD builds the OpenAI request, adds the API key, and returns the [unified response](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/#response-format) with the generated text and the tokens consumed:

```json
{
  "ai_gateway_response": [
    {
      "contents": [
        "An API gateway is a single entry point that routes, secures, and manages the traffic between clients and backend services."
      ]
    }

  "usage": "52"

```

From here, add authentication to the endpoint, more providers to the inventory, an [AI Router](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/) to choose among them, and a [token budget](https://www.krakend.io/docs/enterprise/ai-gateway/budget-control/) to cap the spend.

# [Unified LLM Interface (available in KrakenD Enterprise)](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/)

The **unified LLM interface** is the `ai/llm` component that connects a KrakenD backend to a Large Language Model (LLM) vendor. Clients send only the prompt in a short, vendor-independent JSON body, and KrakenD builds the vendor-specific payload, adds the credentials, calls the vendor, and turns the answer into the same response format for every vendor. Use it to put OpenAI, Google Gemini, Anthropic, Mistral, AWS Bedrock, or Alibaba Cloud Qwen behind your API without exposing their APIs or keys to clients. Because the client contract never changes, you can switch the model or the vendor behind an endpoint without touching any client.

![ai-gateway-unified-llm.seq.mmd diagram](https://www.krakend.io/images/documentation/diagrams/ai-gateway-unified-llm.seq.mmd.svg)

## How the Unified LLM Interface Works

For every request to a backend with the `ai/llm` component, KrakenD:

1. Reads the client’s request body, which contains the prompt in `contents` and, optionally, a system prompt in `instructions`.
2. Builds the payload the vendor expects with a **prompt template**, adding the model and the variables you configured, such as `temperature` or `max_tokens`.
3. Sends the request to the vendor with the credentials of the configuration, so clients never see the API key.
4. Transforms the vendor’s response with an output template into the unified response, which contains the generated text and the token usage.

The default templates cover each vendor’s chat or completion API, and you can replace them with your own (see [Prompt Templates](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/#prompt-templates)). The component also reports the token usage of every call as [OpenTelemetry](https://www.krakend.io/docs/enterprise/telemetry/opentelemetry/) metrics and trace attributes when you enable telemetry.

## Connecting a Backend to an LLM

You can tell the `ai/llm` component which vendor to use in two ways: by referencing a provider from the LLM provider inventory, which is the recommended option, or by writing the vendor configuration inline in the backend.

### LLM Provider Inventory

The [LLM Provider Inventory](https://www.krakend.io/docs/enterprise/ai-gateway/provider-inventory/) declares each provider once in the root `extra_config` under the `ai/providers` namespace, with its vendor, model, and credentials. Backends then reference it by `name`. The following configuration declares an OpenAI provider and exposes it on `/chat`:

```json
{
  "$schema": "https://www.krakend.io/schema/krakend.json",
  "version": 4,
  "extra_config": {
    "ai/providers": {
      "providers": [
        {
          "name": "chat",
          "provider": "openai",
          "model": "gpt-5-nano",
          "credentials": "xxx"
        }
      ]
    }
  },
  "endpoints": [
    {
      "endpoint": "/chat",
      "method": "POST",
      "backend": [
        {
          "extra_config": {
            "ai/llm": {
              "provider": "chat"
            }
          }
        }
      ]
    }
  ]
}
```

The backend needs neither `host` nor `url_pattern`, because KrakenD sends the request to the provider’s endpoint, the OpenAI default in this case. To move `/chat` to another model or vendor, change the `chat` entry and every backend that references it follows. The same inventory feeds the [AI Router](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/), which chooses a provider on each request.

### Inline Vendor Configuration

Instead of a provider reference, the `ai/llm` component accepts a vendor block keyed by the vendor name and the API version. In this case, the backend sets the `host` and `url_pattern` of the vendor API itself:

```json
{
  "endpoint": "/chat",
  "method": "POST",
  "backend": [
    {
      "host": ["https://api.openai.com"],
      "url_pattern": "/v1/responses",
      "extra_config": {
        "ai/llm": {
          "openai": {
            "v1": {
              "credentials": "xxx",
              "variables": {
                "model": "gpt-5-nano"
              }
            }
          }
        }
      }
    }
  ]
}
```

This backend behaves like the previous example. Use the inline form when a backend needs a vendor configuration that no other backend shares, or to keep configurations written before the inventory existed. Each vendor page documents its block and the accepted `variables`:

- [OpenAI](https://www.krakend.io/docs/enterprise/ai-gateway/openai/)
- [Google Gemini](https://www.krakend.io/docs/enterprise/ai-gateway/gemini/)
- [Mistral](https://www.krakend.io/docs/enterprise/ai-gateway/mistral/)
- [Anthropic](https://www.krakend.io/docs/enterprise/ai-gateway/anthropic/)
- [AWS Bedrock](https://www.krakend.io/docs/enterprise/ai-gateway/bedrock/)
- [Alibaba Cloud (Qwen)](https://www.krakend.io/docs/enterprise/ai-gateway/alibaba/)

To reach a vendor that is not on this list, see [Other AI Vendors](https://www.krakend.io/docs/enterprise/ai-gateway/other-vendors/).

The `ai/llm` namespace takes either a `provider` reference or exactly one vendor block, keyed by `openai`, `gemini`, `mistral`, `anthropic`, `bedrock`, or `alibaba`, whose fields are documented on each vendor page. Next to a vendor block, `format` sets the wire format of [streaming](https://www.krakend.io/docs/enterprise/ai-gateway/llm-streaming/) responses. With a `provider` reference, set `format` in the inventory entry instead:

##### Fields of the ai/llm namespace

\* required fields

##### [`format`](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/#format "Click to copy link to format")

Wire format KrakenD exposes to the client for streaming responses, when not defined, the request and response format is not modified. Only anthropic and openai stream formats are supported client-side, regardless of the upstream connector. When defined, KrakenD translates the client’s request into the upstream connector’s format, and translates the streamed response back into this format before returning it.

Possible values are: `"anthropic"` , `"openai"`

##### [`provider`](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/#provider "Click to copy link to provider") string

The `name` of a provider declared in the service-level `ai/providers` configuration. Use it instead of a vendor block so you declare the connection settings once and reuse them on every backend.

Example: `"fast-chat"`

Schema: [https://www.krakend.io/schema/v3.0/ai/llm.json](https://www.krakend.io/schema/v3.0/ai/llm.json "JSON schema definition")

## Request Format

On endpoints that return the full completion, clients send a JSON body with these fields, whatever the vendor behind the endpoint:

- `contents` (required): the prompt, as a string.
- `instructions` (optional): a system prompt that sets the behavior of the model.

For example, with the `/chat` endpoint of the previous examples:

Send a prompt through the unified LLM interface 

```
$curl -XPOST --json '{"instructions": "Answer in one sentence", "contents": "What is an API gateway?"}' http://localhost:8080/chat
```

Clients cannot set the model, the system configuration, or any other part of the vendor payload, because the prompt template only reads these two fields. This keeps the payload under your control and prevents clients from injecting their own system directives or picking a more expensive model.

## Response Format

The default output template returns the generated text inside `ai_gateway_response`, together with the total number of tokens the call consumed in `usage`:

```json
{
  "ai_gateway_response": [
    {
      "contents": [
        "An API gateway is a single entry point that routes, secures, and manages the traffic between clients and backend services."
      ]
    }
  ],
  "usage": "52"
}
```

The `usage` value is a string. Use it to enforce [token budgets](https://www.krakend.io/docs/enterprise/ai-gateway/budget-control/) with the quota component, which reads string values too. When you prefer another name for `ai_gateway_response`, add a [`mapping`](https://www.krakend.io/docs/enterprise/backends/data-manipulation/#mapping) to the backend instead of writing a custom template:

```json
{
  "mapping": {
    "ai_gateway_response": "answer"
  }
}
```

## Prompt Templates

**Prompt templates** define how KrakenD talks to each vendor. The input template builds the payload sent to the LLM, and the output template builds the response returned to the client. Every vendor has a default pair, documented on its page, and you can replace either of them with your own [Go template](https://pkg.go.dev/text/template) file:

- `input_template`: the path to the template that builds the request payload.
- `output_template`: the path to the template that transforms the vendor response.

Both options go in the provider entry of the inventory or in the inline vendor block. Custom templates let you add placeholders, read values from other parts of the request, or fix part of the prompt, so the client only fills the gaps. The templates can access these values:

| Value                                             | Available in     | Content                                                          |
|---------------------------------------------------|------------------|------------------------------------------------------------------|
| `.req_body`                                       | Input and output | The request body sent by the client                              |
| `.req_headers`                                    | Input and output | The request headers listed in the endpoint’s `input_headers`     |
| `.req_params`                                     | Input and output | The parameters of the endpoint URL                               |
| `.req_querystring`                                | Input and output | The query strings listed in the endpoint’s `input_query_strings` |
| `.req_path` and `.req_method`                     | Input and output | The path and method of the request                               |
| `.variables`                                      | Input and output | The `variables` of the configuration, including `extra_payload`  |
| `.resp_body`, `.resp_headers`, and `.resp_status` | Output           | The vendor response                                              |

The `variables.extra_payload` object holds any extra attribute your custom input template needs, accessible as `{{ .variables.extra_payload.yourkey }}`. The default templates ignore it. Templates support the same functions as the [request body generator](https://www.krakend.io/docs/enterprise/backends/body-generator/).

When your output template drops the `usage` field, the [quota](https://www.krakend.io/docs/enterprise/ai-gateway/budget-control/) can no longer count tokens from the response. The token metrics are not affected, because KrakenD reads them from the vendor response before the output template runs.

## Streaming LLM Responses

By default, KrakenD waits for the full completion before answering. To forward the tokens as the model produces them, see [LLM Streaming](https://www.krakend.io/docs/enterprise/ai-gateway/llm-streaming/). Streaming endpoints do not use the request and response format of this page: clients send their requests and receive the stream in the wire format of a vendor, either the vendor behind the endpoint or the OpenAI or Anthropic format you choose with `format`.

# [LLM Provider Inventory (available in KrakenD Enterprise)](https://www.krakend.io/docs/enterprise/ai-gateway/provider-inventory/)

The **LLM provider inventory** is a service-level list of reusable LLM provider configurations declared under the `ai/providers` namespace. You define each provider once, giving it a unique `name` together with the vendor, model, and credentials it needs, and then reference that provider by name from the [`ai/llm` component](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/) or the [AI Router](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/) instead of repeating the full configuration on every backend. Use it whenever several endpoints connect to the same providers, so credentials, models, and endpoints live in a single place. A usable entry needs only two or three fields, and it is the recommended way to configure LLM connections in KrakenD.

Keep provider credentials out of the configuration file

The `credentials` of each provider live in your configuration. Inject them through environment variables with [Flexible Configuration](https://www.krakend.io/docs/enterprise/configuration/flexible-config/) instead of writing the keys in plain text, and restrict access to the configuration file.

## Declaring Providers

You declare the inventory in the root `extra_config` using the `ai/providers` namespace. The namespace holds a single `providers` list, where each entry describes one provider configuration. The minimum a usable entry needs is a `name` and a `provider` (the vendor: `openai`, `gemini`, `anthropic`, `mistral`, `bedrock`, or `alibaba`). Set `credentials` to the API key of the vendor. When you leave it empty, KrakenD sends no authentication header, which only suits servers that require no key, such as a local [OpenAI-compatible server](https://www.krakend.io/docs/enterprise/ai-gateway/other-vendors/#openai-compatible-servers). When you omit `endpoint` or `model`, KrakenD uses the [vendor’s defaults](https://www.krakend.io/docs/enterprise/ai-gateway/provider-inventory/#default-endpoints-and-models).

The following configuration declares seven providers across five vendors:

```json
{
  "$schema": "https://www.krakend.io/schema/krakend.json",
  "version": 4,
  "extra_config": {
    "ai/providers": {
      "providers": [
        {
          "name": "cheap-quick",
          "provider": "openai",
          "endpoint": "https://custom-self-hosted.example.com/v1/responses",
          "model": "gpt-4o-mini",
          "credentials": "xxx"
        },
        {
          "name": "gpt-default",
          "provider": "openai",
          "credentials": "xxx"
        },
        {
          "name": "gemini-flash",
          "provider": "gemini",
          "model": "gemini-2.5-flash",
          "credentials": "xxx"
        },
        {
          "name": "coding-basic",
          "provider": "anthropic",
          "model": "claude-haiku-4-5",
          "credentials": "xxx"
        },
        {
          "name": "coding-team",
          "provider": "anthropic",
          "model": "claude-sonnet-4-6",
          "credentials": "xxx"
        },
        {
          "name": "reasoning",
          "provider": "mistral",
          "credentials": "xxx"
        },
        {
          "name": "summaries",
          "provider": "bedrock",
          "model": "eu.amazon.nova-lite-v1:0",
          "credentials": "xxx",
          "debug": true,
          "variables": {
            "max_tokens": 1500
          }
        }
      ]
    }
  }
}
```

The `cheap-quick` entry points to a self-hosted OpenAI-compatible endpoint, while the rest rely on each vendor’s default endpoint. The `gpt-default` and `reasoning` entries set only a vendor and credentials, so they also use the vendor’s default model. Replace every `"xxx"` with your real credentials, preferably through an environment variable.

Besides the vendor, model, endpoint, and credentials, a provider entry accepts these options:

- `variables` carries provider-specific parameters such as `temperature` or `max_tokens`. The accepted keys depend on the `provider` and match the variables documented on each vendor’s page, such as [OpenAI](https://www.krakend.io/docs/enterprise/ai-gateway/openai/) or [Anthropic](https://www.krakend.io/docs/enterprise/ai-gateway/anthropic/).
- `input_template` and `output_template` point to [Go template](https://pkg.go.dev/text/template) files that replace the default request payload and response transformation. See [Prompt Templates](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/#prompt-templates).
- `streaming` and `format` turn the provider into a streaming one, as explained in [Streaming Providers](https://www.krakend.io/docs/enterprise/ai-gateway/provider-inventory/#streaming-providers).
- `debug` logs the provider activity for troubleshooting. Do not enable it in production, as it may log sensitive data.

These are all the fields of the `ai/providers` namespace:

##### Fields of AI Providers

\* required fields

##### [`providers`](https://www.krakend.io/docs/enterprise/ai-gateway/provider-inventory/#providers "Click to copy link to providers") * array of objects

The array of AI providers available for referencing from the backends. Each object is a different provider declaration.

Each item of providers accepts the following properties:

##### [`credentials`](#providers-credentials "Click to copy link to credentials") string

The API key used to authenticate against the provider. Inject it with an environment variable instead of writing it in the configuration.

##### [`debug`](#providers-debug "Click to copy link to debug") boolean

Enables the debug mode to log activity for troubleshooting. Do not set this value to `true` in production as it may log sensitive data.

Defaults to `false`

##### [`endpoint`](#providers-endpoint "Click to copy link to endpoint") string

Overrides the default API endpoint of the provider. Set it when you need to reach a proxy, a private deployment, or a region-specific host instead of the vendor’s public API. When you don’t set it, each provider uses its own default endpoint. Gemini and Bedrock build theirs from the `model` and `streaming` values, so their default shown here corresponds to the default `model` without streaming.

##### [`format`](#providers-format "Click to copy link to format")

Wire format KrakenD exposes to the client for streaming responses, when not defined, the request and response format is not modified. Only anthropic and openai stream formats are supported client-side, regardless of the upstream connector. When defined, KrakenD translates the client’s request into the upstream connector’s format, and translates the streamed response back into this format before returning it.

Possible values are: `"anthropic"` , `"openai"`

##### [`input_template`](#providers-input_template "Click to copy link to input_template") string

A path to a custom [Go template](https://pkg.go.dev/text/template) that sets the payload format sent to the provider. You don’t need to set this value unless you want to override the default template making use of all the `variables` listed in this configuration.

##### [`model`](#providers-model "Click to copy link to model") string

The name of the model you want to use. The value you provide is passed as is to the provider and KrakenD does not check if the model is currently accepted by the vendor. Check the available models on the vendor documentation. When you don’t set it, each provider uses its own default model.

##### [`name`](#providers-name "Click to copy link to name") * string

A unique name for this provider declaration. This is the name you use to reference the provider from the backends, so you declare its settings once and reuse them everywhere.

Example: `"fast-chat"`

##### [`output_template`](#providers-output_template "Click to copy link to output_template") string

A path to a custom [Go template](https://pkg.go.dev/text/template) that sets how the response from the provider is transformed before being sent to the client. The default template extracts the text from the first choice returned by the provider so in most cases you don’t need to set a custom output template.

##### [`provider`](#providers-provider "Click to copy link to provider") *

The AI vendor this declaration connects to. The chosen vendor determines which `variables` are accepted.

Possible values are: `"anthropic"` , `"bedrock"` , `"gemini"` , `"mistral"` , `"openai"` , `"alibaba"`

##### [`streaming`](#providers-streaming "Click to copy link to streaming") boolean

Enables streaming responses, so the tokens generated by the model are forwarded to the client as they are produced instead of waiting for the complete response.

Defaults to `false`

##### [`variables`](#providers-variables "Click to copy link to variables") object

The variables KrakenD uses to build the payload for the chosen `provider`.

Schema: [https://www.krakend.io/schema/v3.0/ai/providers.json](https://www.krakend.io/schema/v3.0/ai/providers.json "JSON schema definition")

## Referencing a Provider from a Backend

Once a provider exists in the inventory, the `ai/llm` component references it by `name` with a single `provider` property, instead of an inline vendor block:

```json
{
  "endpoint": "/chat",
  "method": "POST",
  "backend": [
    {
      "extra_config": {
        "ai/llm": {
          "provider": "cheap-quick"
        }
      }
    }
  ]
}
```

The backend above resolves the `cheap-quick` provider from the inventory and sends the request to its `endpoint`, with its model and credentials, so it needs neither `host` nor `url_pattern`. Because you reference the provider by name, you can reuse it across many backends and change its definition in one place.

When `ai/llm` references a provider, it accepts no other option: every setting, including `format`, belongs to the inventory entry. To choose among several providers on each request, based on headers, policies, or a classifier, use the [AI Router](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/), which references the same inventory.

## Streaming Providers

Set `streaming` to `true` in a provider entry to forward the tokens to the client as the model produces them. Add `format` to normalize the streamed output to the `openai` or `anthropic` wire format, regardless of the vendor behind the provider. [LLM Streaming](https://www.krakend.io/docs/enterprise/ai-gateway/llm-streaming/) explains both options in detail.

The `streaming` flag of the provider must match the endpoint that uses it: a streaming provider requires an endpoint with a streaming `output_encoding`, and a non-streaming provider requires an endpoint without it. When they do not match, the endpoint answers every request with a `500` status code, and KrakenD logs an error like this one at startup:

```log
KRAKEND ERROR: [BACKEND: POST /chat -> POST /][AI/LLM] Failed to load provider: gemini-stream provider gemini-stream streaming flag true does not match backend encoding
```

Declare two entries for the same model when you need it both with and without streaming.

The following configuration streams Gemini responses in the OpenAI format:

```json
{
  "$schema": "https://www.krakend.io/schema/krakend.json",
  "version": 4,
  "extra_config": {
    "ai/providers": {
      "providers": [
        {
          "name": "gemini-stream",
          "provider": "gemini",
          "model": "gemini-2.5-flash",
          "credentials": "xxx",
          "streaming": true,
          "format": "openai"
        }
      ]
    }
  },
  "endpoints": [
    {
      "endpoint": "/v1/responses",
      "method": "POST",
      "output_encoding": "streaming",
      "backend": [
        {
          "extra_config": {
            "ai/llm": {
              "provider": "gemini-stream"
            }
          }
        }
      ]
    }
  ]
}
```

Clients send OpenAI Responses requests to `/v1/responses` and receive an OpenAI-formatted stream, while Gemini serves the request. Because `streaming` is `true`, KrakenD calls Gemini’s streaming endpoint automatically. For example:

Stream a Gemini response in the OpenAI format 

```
$curl -N -XPOST --json '{"input": "Tell me a joke", "stream": true}' http://localhost:8080/v1/responses
```

The response arrives as Server-Sent Events with the OpenAI Responses event types, such as `response.output_text.delta`, and ends with a `response.completed` event that carries the token usage.

## Default Endpoints and Models

When you omit `model` in a provider entry, KrakenD uses the default model of the vendor:

| Provider                                                          | Default model              |
|-------------------------------------------------------------------|----------------------------|
| [OpenAI](https://www.krakend.io/docs/enterprise/ai-gateway/openai/) (`openai`)          | `gpt-5.4-mini`             |
| [Google Gemini](https://www.krakend.io/docs/enterprise/ai-gateway/gemini/) (`gemini`)   | `gemini-3.5-flash`         |
| [Anthropic](https://www.krakend.io/docs/enterprise/ai-gateway/anthropic/) (`anthropic`) | `claude-haiku-4-5`         |
| [Mistral](https://www.krakend.io/docs/enterprise/ai-gateway/mistral/) (`mistral`)       | `mistral-small-latest`     |
| [AWS Bedrock](https://www.krakend.io/docs/enterprise/ai-gateway/bedrock/) (`bedrock`)   | `eu.amazon.nova-lite-v1:0` |
| [Alibaba Cloud](https://www.krakend.io/docs/enterprise/ai-gateway/alibaba/) (`alibaba`) | `qwen3.8-flash`            |

When you omit `endpoint`, KrakenD sends the requests to the default endpoint of the `provider`:

```text
openai     https://api.openai.com/v1/responses
gemini     https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent
anthropic  https://api.anthropic.com/v1/messages
mistral    https://api.mistral.ai/v1/chat/completions
bedrock    https://bedrock-runtime.eu-west-1.amazonaws.com/model/{model}/converse
alibaba    https://token-plan.ap-southeast-1.maas.aliyuncs.com/compatible-mode/v1/responses
```

The Gemini and Bedrock default endpoints embed the selected `model` in the URL. With `streaming` enabled, they also switch to the vendor’s streaming method: Gemini uses `{model}:streamGenerateContent?alt=sse` and Bedrock uses `{model}/converse-stream`. The other vendors stream through the same endpoint. The Bedrock default targets the `eu-west-1` region; set `endpoint` to use a different region.

# [LLM Routing Strategies (available in KrakenD Enterprise)](https://www.krakend.io/docs/enterprise/ai-gateway/llm-routing/)

**LLM routing** decides which Large Language Model (LLM) serves each request that reaches your AI endpoints. In KrakenD, the [AI Router](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/) covers the most common case: it picks one provider from the [LLM provider inventory](https://www.krakend.io/docs/enterprise/ai-gateway/provider-inventory/) on every request, based on headers, policies, JWT claims, or a classifier, with failover when a provider fails. Other needs, such as giving clients the vendor’s own API, asking several models at once, or mixing AI and non-AI backends, use other KrakenD features described on this page. Choosing the right strategy keeps model selection under your control instead of the client’s.

## Choosing a Routing Strategy

Pick the strategy that matches what you need:

| You need to                                                                                            | Use                                                                                             |
|--------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------|
| Choose one provider per request from headers, JWT claims, CEL policies, or a classifier, with failover | [AI Router](https://www.krakend.io/docs/enterprise/ai-gateway/llm-routing/#routing-with-the-ai-router)                |
| Offer a fixed provider on each endpoint, such as `/llm/openai` and `/llm/anthropic`                    | [One endpoint per provider](https://www.krakend.io/docs/enterprise/ai-gateway/llm-routing/#one-endpoint-per-provider) |
| Let clients use the vendor’s own API, for example through its SDK                                      | [Vendor-native passthrough](https://www.krakend.io/docs/enterprise/ai-gateway/llm-routing/#vendor-native-passthrough) |
| Ask several LLMs at once and return all the answers                                                    | [Multi-LLM aggregation](https://www.krakend.io/docs/enterprise/ai-gateway/llm-routing/#multi-llm-aggregation)         |
| Send some requests to an LLM and the rest to a regular backend                                         | [Conditional routing](https://www.krakend.io/docs/enterprise/ai-gateway/llm-routing/#mixing-llm-and-non-llm-backends) |

## Routing with the AI Router

The [AI Router](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/) evaluates an ordered list of routes in the `ai/router` namespace of a backend, and each route sends the request to a provider of the inventory when its **gates** pass. Clients call a single endpoint and never choose the model.

Route on values the client cannot forge. A JWT claim is a good example: the following configuration validates the token, [propagates](https://www.krakend.io/docs/enterprise/authorization/jwt-validation/#propagate-jwt-claims-as-request-headers) its `plan` claim as the `X-Plan` header, and sends `premium` users to a larger model:

```json
{
  "$schema": "https://www.krakend.io/schema/krakend.json",
  "version": 4,
  "extra_config": {
    "ai/providers": {
      "providers": [
        {
          "name": "small",
          "provider": "openai",
          "model": "gpt-5-nano",
          "credentials": "xxx"
        },
        {
          "name": "large",
          "provider": "anthropic",
          "model": "claude-sonnet-4-6",
          "credentials": "xxx"
        }
      ]
    },
    "ai/classifiers": {
      "gates": [
        {
          "name": "plan_premium",
          "rule": "header",
          "header": {
            "name": "X-Plan",
            "value": "premium"
          }
        }
      ]
    }
  },
  "endpoints": [
    {
      "endpoint": "/chat",
      "method": "POST",
      "input_headers": ["X-Plan"],
      "extra_config": {
        "auth/validator": {
          "alg": "RS256",
          "jwk_url": "https://idp.example.com/.well-known/jwks.json",
          "cache": true,
          "propagate_claims": [
            ["plan", "X-Plan"]
          ]
        }
      },
      "backend": [
        {
          "extra_config": {
            "ai/router": {
              "routes": [
                {
                  "provider": "large",
                  "gates": ["plan_premium"]
                },
                {
                  "provider": "small"
                }
              ]
            }
          }
        }
      ]
    }
  ]
}
```

Users whose token carries `"plan": "premium"` reach the `large` provider, and everyone else falls through to `small`. Because the identity provider issues the claim and KrakenD sets the header from the validated token, users cannot pick the model themselves. The [AI Router](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/) page covers policy gates, nested decision trees, classifiers, and failover.

## One Endpoint per Provider

The simplest strategy declares one endpoint for each provider and lets the client choose by calling one or the other. With the `small` and `large` providers of the previous example, each endpoint has a backend that references its provider:

```json
{
  "endpoints": [
    {
      "endpoint": "/llm/openai",
      "method": "POST",
      "backend": [
        {
          "extra_config": {
            "ai/llm": {
              "provider": "small"
            }
          }
        }
      ]
    },
    {
      "endpoint": "/llm/anthropic",
      "method": "POST",
      "backend": [
        {
          "extra_config": {
            "ai/llm": {
              "provider": "large"
            }
          }
        }
      ]
    }
  ]
}
```

Both endpoints accept the same [unified request format](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/#request-format), so switching vendors is a matter of changing the path. Use it when the client legitimately decides the model, for example in an internal tool, and protect each endpoint with its own authorization or [quota](https://www.krakend.io/docs/enterprise/ai-gateway/budget-control/) when the costs differ.

## Vendor-Native Passthrough

Some clients need the vendor’s own API, for instance an official SDK or a coding agent that uses features beyond a prompt, such as tools or file uploads. In that case, proxy the vendor API without any AI processing, using the [`no-op` encoding](https://www.krakend.io/docs/enterprise/endpoints/no-op/), and keep the API key on the gateway with a [Martian header modifier](https://www.krakend.io/docs/enterprise/backends/martian/#header-modifier):

```json
{
  "endpoint": "/v1/responses",
  "method": "POST",
  "output_encoding": "no-op",
  "extra_config": {
    "auth/validator": {
      "alg": "RS256",
      "jwk_url": "https://idp.example.com/.well-known/jwks.json",
      "cache": true
    }
  },
  "backend": [
    {
      "host": ["https://api.openai.com"],
      "url_pattern": "/v1/responses",
      "encoding": "no-op",
      "extra_config": {
        "modifier/martian": {
          "header.Modifier": {
            "scope": ["request"],
            "name": "Authorization",
            "value": "Bearer YOUR_OPENAI_API_KEY"
          }
        }
      }
    }
  ]
}
```

Clients point their OpenAI SDK at KrakenD and authenticate with their own JWT, while only the gateway knows the OpenAI key. KrakenD forwards the payload as is, so you lose what the `ai/llm` component adds: the payload stays under the client’s control, the response keeps the vendor format, and KrakenD does not report token metrics.

When your clients only need chat and streaming, consider the [`format` option of LLM streaming](https://www.krakend.io/docs/enterprise/ai-gateway/llm-streaming/#normalizing-the-output-format-with-format) instead. It accepts requests in the OpenAI or Anthropic format and serves them from any vendor, keeping the token metrics and the provider inventory.

## Multi-LLM Aggregation

To ask several models the same question in a single call, add one backend per provider to the endpoint. KrakenD calls them in parallel and merges their responses, and the [`group`](https://www.krakend.io/docs/enterprise/backends/data-manipulation/#grouping) option keeps each answer under its own key:

```json
{
  "endpoint": "/compare",
  "method": "POST",
  "backend": [
    {
      "group": "openai",
      "extra_config": {
        "ai/llm": {
          "provider": "small"
        }
      }
    },
    {
      "group": "anthropic",
      "extra_config": {
        "ai/llm": {
          "provider": "large"
        }
      }
    }
  ]
}
```

The response contains an `openai` and an `anthropic` object, each with its own `ai_gateway_response` and `usage`. Use it to compare models, or to let the client pick the best answer. Every call consumes tokens from each provider.

## Mixing LLM and Non-LLM Backends

[Conditional Routing](https://www.krakend.io/docs/enterprise/backends/conditional/) decides which backend of an endpoint runs, with header or policy conditions and a `fallback` backend. Use it when only some requests need an LLM and the rest go to a regular service. For example, premium users get an answer generated by an LLM, while everyone else gets the results of the regular search service:

```json
{
  "endpoint": "/search",
  "method": "POST",
  "input_headers": ["X-Plan"],
  "extra_config": {
    "auth/validator": {
      "alg": "RS256",
      "jwk_url": "https://idp.example.com/.well-known/jwks.json",
      "cache": true,
      "propagate_claims": [
        ["plan", "X-Plan"]
      ]
    }
  },
  "backend": [
    {
      "extra_config": {
        "backend/conditional": {
          "strategy": "policy",
          "value": "getHeader('X-Plan') == 'premium'"
        },
        "ai/llm": {
          "provider": "large"
        }
      }
    },
    {
      "host": ["http://search.example.com"],
      "url_pattern": "/search",
      "extra_config": {
        "backend/conditional": {
          "strategy": "fallback"
        }
      }
    }
  ]
}
```

The policy reads the propagated claim, which is why `X-Plan` is in the `input_headers` list. When it evaluates to `false`, the `fallback` backend serves the request. To choose among several LLMs instead of between an LLM and a regular backend, prefer the [AI Router](https://www.krakend.io/docs/enterprise/ai-gateway/llm-routing/#routing-with-the-ai-router), which adds classifiers and failover.

# [AI Router for LLM Provider Selection (available in KrakenD Enterprise)](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/)

The **AI Router** selects which LLM provider from your [provider inventory](https://www.krakend.io/docs/enterprise/ai-gateway/provider-inventory/) handles each request. It matches requests with reusable **gates** (header or policy conditions), organizes them into an ordered decision tree, and can hand the final choice to a **classifier** that picks the best provider from a candidate list. A failover takes over when a classifier or the chosen provider fails, and a final route without gates catches the requests that match no other route. Because routes reference providers by name, the client sends its request to a single endpoint and never selects a model or vendor; the router decides.

Requires the provider inventory

Routes and classifiers reference providers by `name`, so define your providers first in the [LLM provider inventory](https://www.krakend.io/docs/enterprise/ai-gateway/provider-inventory/) (`ai/providers`). The router resolves the vendor, model, endpoint, and credentials from that inventory.

## How the AI Router Works

You configure routing in two places. Gates and classifiers are shared, reusable definitions declared once at the service level under the `ai/classifiers` namespace. The routing rules that use them live in a backend’s `extra_config` under the `ai/router` namespace, in an ordered `routes` list.

For each request, KrakenD evaluates the routes from top to bottom and uses the first one that matches. A route matches when any of its gates passes; a route with no gates always matches, so you can use it as an inline fallback. When no route matches and there is no such route, the request fails: the failover does not apply to requests that match no route. When the matching route names a `provider`, the router forwards the request to that provider from the inventory. When it names a `classifier` and a list of `providers`, the classifier chooses among them. Routes can also nest, forming a decision tree: a gated route holds its own `routes`, evaluated only when its gates pass. Nesting is how you require several gates at once.

Route on signals the client cannot forge

Header gates match on request headers, which clients control. Route on values your gateway sets, for example a plan or tier header injected after validating an API key or JWT, so a client cannot select a more expensive model by sending a header itself.

## Defining Gates

A **gate** is a named matching condition declared under `ai/classifiers.gates`. Routes reference gates by name, and you can reuse the same gate across many routes. Each gate has a `name`, a `rule` that selects the matching mechanism (`header` or `policy`), and the configuration for that rule.

### Header Gates

A `header` gate matches when a request header equals a value. Set `header.name` and `header.value`:

```json
{
  "name": "plan_enterprise",
  "rule": "header",
  "header": {
    "name": "X-Plan",
    "value": "enterprise"
  }
}
```

The gate above matches requests that carry `X-Plan: enterprise`.

### Policy Gates

A `policy` gate matches when a CEL expression evaluates to true. Set `policy.value` to the expression, using helper functions such as `hasHeader` and `getHeader` (see the [policy built-in functions](https://www.krakend.io/docs/enterprise/security-policies/built-in-functions/)):

```json
{
  "name": "enterprise_policy",
  "rule": "policy",
  "policy": {
    "value": "getHeader('X-Plan') == 'enterprise'"
  }
}
```

Policy gates handle conditions a header match cannot express, such as comparing values or combining several checks.

## Defining Classifiers

A **classifier** delegates the provider choice to an external engine that scores the request against a set of candidate providers and returns the best fit. Declare classifiers under `ai/classifiers.classifiers`. Each has a `name`, an `engine`, and the engine’s configuration. The supported engine is `notdiamond`, which calls the [Not Diamond](https://notdiamond.ai/) [model selection endpoint](https://docs.notdiamond.ai/reference/token_model_select_v2_modelrouter_modelselect_post) to pick the best provider:

```json
{
  "name": "smart",
  "engine": "notdiamond",
  "notdiamond": {
    "credentials": "xxx",
    "req_content": "req_body.messages"
  }
}
```

The `credentials` authenticate against the Not Diamond service; set them through an environment variable. The `req_content` field selects the request content sent to the classifier, and it works exactly like the same field in the [Semantic Cache](https://www.krakend.io/docs/enterprise/ai-gateway/semantic-cache/#selecting-the-content-to-match). It defaults to the full `req_body`, and you can point it at any request input source:

- `req_body`: the request body. Use [dot-notation](https://www.krakend.io/docs/enterprise/endpoints/request-body-extractor/) to reach nested fields, for example `req_body.messages`.
- `req_params`: a URL path parameter. The key is capitalized, so `{id}` is exposed as `req_params.Id`.
- `req_query_string`: a query string value, for example `req_query_string.user`.
- `req_headers`: a request header, for example `req_headers.x-user`.

The `tradeoff` option tells Not Diamond whether to favor `cost` (the default) or `latency`, while `cost_quality_tradeoff` balances cost against quality with an integer. They are mutually exclusive: set one or the other, not both.

## Routing Requests

Add the `ai/router` namespace to a backend’s `extra_config`. It holds an ordered `routes` list and an optional `failover` provider.

### Matching with Gates

Each route lists the `gates` it checks. KrakenD evaluates them in order, and the route matches as soon as one of them passes. A route with no `gates` always matches, so place it last as an inline fallback. A matching route forwards the request to its `provider`:

```json
{
  "ai/router": {
    "routes": [
      {
        "provider": "coding-basic",
        "gates": ["plan_pro"]
      },
      {
        "provider": "cheap-quick"
      }
    ]
  }
}
```

Pro-plan requests go to `coding-basic`; every other request falls through to `cheap-quick`.

Listing several gates in one route combines them with OR: `"gates": ["plan_pro", "region_eu"]` matches every pro-plan request and every EU request. To require all of them (AND), nest the routes as shown in [Nested Routes and Decision Trees](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/#nested-routes-and-decision-trees), or combine the checks in a single [policy gate](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/#policy-gates), for example `getHeader('X-Plan') == 'pro' && getHeader('X-Region') == 'eu'`.

### Nested Routes and Decision Trees

The `routes` field is recursive. A gated route can hold its own `routes`, evaluated only when its gates pass, and those can nest further to any depth, forming a decision tree. A route that only groups other routes needs no `provider`; the matching leaf route selects it:

```json
{
  "ai/router": {
    "routes": [
      {
        "gates": ["plan_enterprise"],
        "routes": [
          {
            "provider": "coding-team",
            "gates": ["usecase_code"]
          },
          {
            "provider": "gemini-flash"
          }
        ]
      },
      {
        "provider": "cheap-quick"
      }
    ]
  }
}
```

Enterprise-plan requests enter the branch and route to `coding-team` for code tasks (gate `usecase_code`), or to the branch fallback `gemini-flash`. Only requests that pass both `plan_enterprise` and `usecase_code` reach `coding-team`: each nesting level adds a condition. Any other plan skips the branch and hits the top-level fallback `cheap-quick`.

### Classifier Routes

Instead of a single `provider`, a route can name a `classifier` and a list of candidate `providers`. The classifier chooses the best provider for each request from that list. A route cannot set both `provider` and `classifier`:

```json
{
  "ai/router": {
    "failover": "gpt-default",
    "routes": [
      {
        "gates": ["enterprise_policy"],
        "classifier": "smart",
        "providers": [
          "cheap-quick",
          "gemini-flash",
          "coding-basic"
        ],
        "failover": "coding-basic"
      },
      {
        "provider": "cheap-quick"
      }
    ]
  }
}
```

Enterprise requests are handed to the `smart` classifier, which picks among `cheap-quick`, `gemini-flash`, and `coding-basic`. If the classifier cannot return a choice, or the provider it picked fails, the route’s own `failover` sends the request to `coding-basic`. Every other request falls through to `cheap-quick`, the final route without gates; if `cheap-quick` fails, the router-level `failover` sends the request to `gpt-default`.

### Failover and Fallback

The router has two different safety nets.

**Failover** handles errors. It names the provider that serves the request when a classifier cannot return a choice, or when the provider a route chose fails (an error response from the provider). You can set it at two levels:

- **Route failover**: a `failover` inside a route covers that route. On a route with a `provider`, it serves the request when that provider fails. On a route with a `classifier`, it serves the request when the classifier cannot return a choice or the provider it chose fails. It takes precedence over the router-level failover.
- **Router failover**: the `failover` next to `routes` covers every route that sets no failover of its own, whether it names a `provider` or a `classifier`.

**Fallback** handles requests that match no route. Place a route without `gates` and without `classifier` last in `routes`: it always matches, so it catches every request the routes above it do not. The failover does not apply to requests that match no route. Without a fallback route, such a request fails with an error.

| Situation                                        | Who serves the request                                        |
|--------------------------------------------------|---------------------------------------------------------------|
| A route matches and its provider answers         | That provider                                                 |
| The classifier of a route cannot return a choice | The route failover, or else the router failover               |
| The provider a route chose fails                 | The route failover, or else the router failover               |
| No route matches                                 | The final route without gates; without one, the request fails |

The following fields are available under the backend-level `ai/router` namespace:

##### Fields of AI Router

\* required fields

##### [`failover`](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/#failover "Click to copy link to failover") string

The name of the provider in the `ai/providers` inventory that handles the request when a classifier cannot return a choice, or when the provider a route chose fails, and that route sets no `failover` of its own. It does not apply to requests that match no route: place a route without `gates` last in `routes` for those.

Example: `"gpt-default"`

##### [`routes`](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/#routes "Click to copy link to routes") * array

The ordered list of routes. KrakenD evaluates them from top to bottom and uses the first one that matches. A route without `gates` always matches, so place it last as the fallback for requests that match no other route; without it, such a request fails, even with a `failover`.

Schema: [https://www.krakend.io/schema/v3.0/ai/router.json](https://www.krakend.io/schema/v3.0/ai/router.json "JSON schema definition")

Each object in the `routes` list accepts the following fields:

##### Fields of Route

\* required fields

##### [`classifier`](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/#classifier "Click to copy link to classifier") string

The name of a classifier declared in `ai/classifiers` that chooses the best provider from the `providers` list. You cannot use it together with `provider`.

Example: `"smart"`

##### [`failover`](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/#failover "Click to copy link to failover") string

The provider to use when this route fails. A route fails when its provider returns an error or its classifier cannot pick one. It overrides the router-level `failover`. You cannot use it with `routes`.

Example: `"gpt-default"`

##### [`gates`](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/#gates "Click to copy link to gates") array of strings

The names of the gates declared in `ai/classifiers` that this route checks, in order. The route matches as soon as one of them passes. To require several gates at once, nest routes instead of listing the gates together. Omit it to create a route that always matches.

Example: `["plan_pro","plan_enterprise"]`

##### [`provider`](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/#provider "Click to copy link to provider") string

The name of the provider in the `ai/providers` inventory that handles the request when the route matches. You cannot use it together with `classifier`.

Example: `"cheap-quick"`

##### [`providers`](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/#providers "Click to copy link to providers") array of strings

The names of the providers in the `ai/providers` inventory that the `classifier` chooses from. It requires a `classifier`.

Example: `["cheap-quick","gemini-flash","coding-basic"]`

##### [`routes`](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/#routes "Click to copy link to routes") array

The ordered list of routes that KrakenD evaluates only when the gates of this route pass. Nested routes can go to any depth, forming a decision tree, and a route that only groups other routes needs no `provider`.

Schema: [https://www.krakend.io/schema/v3.0/ai/router.json](https://www.krakend.io/schema/v3.0/ai/router.json "JSON schema definition")

## Configuration Example

The following configuration defines the providers, gates, and a classifier once at the service level, then uses them across two backends. The first backend routes by plan and use case with a decision tree; the second delegates the choice to the classifier and sets a failover:

```json
{
  "$schema": "https://www.krakend.io/schema/krakend.json",
  "version": 4,
  "extra_config": {
    "ai/providers": {
      "providers": [
        {
          "name": "cheap-quick",
          "provider": "openai",
          "model": "gpt-4o-mini",
          "credentials": "xxx"
        },
        {
          "name": "gpt-default",
          "provider": "openai",
          "credentials": "xxx"
        },
        {
          "name": "gemini-flash",
          "provider": "gemini",
          "model": "gemini-2.5-flash",
          "credentials": "xxx"
        },
        {
          "name": "coding-basic",
          "provider": "anthropic",
          "model": "claude-haiku-4-5",
          "credentials": "xxx"
        },
        {
          "name": "coding-team",
          "provider": "anthropic",
          "model": "claude-sonnet-4-6",
          "credentials": "xxx"
        }
      ]
    },
    "ai/classifiers": {
      "gates": [
        {
          "name": "plan_enterprise",
          "rule": "header",
          "header": {
            "name": "X-Plan",
            "value": "enterprise"
          }
        },
        {
          "name": "plan_pro",
          "rule": "header",
          "header": {
            "name": "X-Plan",
            "value": "pro"
          }
        },
        {
          "name": "usecase_code",
          "rule": "header",
          "header": {
            "name": "X-Use-Case",
            "value": "code"
          }
        },
        {
          "name": "enterprise_policy",
          "rule": "policy",
          "policy": {
            "value": "getHeader('X-Plan') == 'enterprise'"
          }
        }
      ],
      "classifiers": [
        {
          "name": "smart",
          "engine": "notdiamond",
          "notdiamond": {
            "credentials": "xxx",
            "req_content": "req_body.messages"
          }
        }
      ]
    }
  },
  "endpoints": [
    {
      "endpoint": "/v1/chat",
      "method": "POST",
      "input_headers": [
        "X-Plan",
        "X-Use-Case"
      ],
      "backend": [
        {
          "extra_config": {
            "ai/router": {
              "routes": [
                {
                  "gates": ["plan_enterprise"],
                  "routes": [
                    {
                      "provider": "coding-team",
                      "gates": ["usecase_code"]
                    },
                    {
                      "provider": "gemini-flash"
                    }
                  ]
                },
                {
                  "provider": "coding-basic",
                  "gates": ["plan_pro"]
                },
                {
                  "provider": "cheap-quick"
                }
              ]
            }
          }
        }
      ]
    },
    {
      "endpoint": "/v1/route",
      "method": "POST",
      "input_headers": [
        "*"
      ],
      "backend": [
        {
          "extra_config": {
            "ai/router": {
              "failover": "gpt-default",
              "routes": [
                {
                  "gates": ["enterprise_policy"],
                  "classifier": "smart",
                  "providers": [
                    "cheap-quick",
                    "gemini-flash",
                    "coding-basic"
                  ]
                },
                {
                  "provider": "cheap-quick"
                }
              ]
            }
          }
        }
      ]
    }
  ]
}
```

On the `/v1/chat` endpoint, enterprise-plan requests enter the nested branch and route to `coding-team` for code tasks or to `gemini-flash` otherwise, pro-plan requests go to `coding-basic`, and any other request falls through to `cheap-quick`. On the `/v1/route` endpoint, enterprise requests are classified by `smart` across three candidate providers; when `smart` cannot decide or the provider it picked fails, `gpt-default` serves them as the failover. Any other request falls through to `cheap-quick`, the final route without gates, and `gpt-default` also takes over if `cheap-quick` fails.

The AI Router is the inventory-based way to choose a provider per request. For other strategies, such as vendor-native passthrough, multi-LLM aggregation, or mixing LLM and non-LLM backends, see [LLM Routing Strategies](https://www.krakend.io/docs/enterprise/ai-gateway/llm-routing/).

# [Streaming LLM Responses with the AI Gateway (available in KrakenD Enterprise)](https://www.krakend.io/docs/enterprise/ai-gateway/llm-streaming/)

**LLM streaming** delivers a large language model’s response to the client incrementally, as the model generates it, instead of waiting for the full completion. It builds on KrakenD’s [HTTP streaming](https://www.krakend.io/docs/enterprise/endpoints/streaming/) support and the `ai/llm` component, so the vendor credentials, the models, and the [provider inventory](https://www.krakend.io/docs/enterprise/ai-gateway/provider-inventory/) stay on the gateway as in non-streaming calls. Use it for chat and agent experiences where users expect tokens to appear in real time. Unlike the [unified request and response format](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/#request-format) of non-streaming calls, clients speak the wire format of a vendor: the one behind the endpoint, or the OpenAI or Anthropic format you choose with the `format` option, so existing SDKs and agents work against KrakenD unchanged.

Streaming outside the AI Gateway

This page covers streaming LLM responses processed by the `ai/llm` component. To proxy an upstream SSE, NDJSON, or event-stream source without any AI-specific processing, see [Streaming and SSE](https://www.krakend.io/docs/enterprise/endpoints/streaming/) instead.

## Enabling LLM Streaming

Streaming needs two settings: `streaming` set to `true` in the provider entry of the inventory, and the endpoint’s `output_encoding` set to `streaming`. Unlike the generic `sse`, `ndjson`, and `eventstream` encodings, `streaming` is a pseudo-encoding reserved for the `ai/llm` component: KrakenD resolves it to the concrete wire format that the vendor and the `format` you configured require. For example, most vendors stream over Server-Sent Events (SSE), while AWS Bedrock streams over the `eventstream` binary framing.

A minimal endpoint that streams an OpenAI response looks like this:

```json
{
  "$schema": "https://www.krakend.io/schema/krakend.json",
  "version": 4,
  "extra_config": {
    "ai/providers": {
      "providers": [
        {
          "name": "gpt-stream",
          "provider": "openai",
          "model": "gpt-5-nano",
          "credentials": "xxx",
          "streaming": true
        }
      ]
    }
  },
  "endpoints": [
    {
      "endpoint": "/v1/responses",
      "method": "POST",
      "output_encoding": "streaming",
      "backend": [
        {
          "extra_config": {
            "ai/llm": {
              "provider": "gpt-stream"
            }
          }
        }
      ]
    }
  ]
}
```

Without `format`, clients send the same request they would send to the OpenAI Responses API, including `"stream": true`, and receive OpenAI’s native stream unchanged. KrakenD adds the credentials and replaces the `model` of the request with the one of the provider, so clients cannot choose a different model:

Stream an OpenAI response through KrakenD 

```
$curl -N -XPOST --json '{"input": "Tell me a joke", "stream": true}' http://localhost:8080/v1/responses
```

The `streaming` flag of the provider must match the endpoint, as explained in [Streaming Providers](https://www.krakend.io/docs/enterprise/ai-gateway/provider-inventory/#streaming-providers). Declare a separate provider entry when you need the same model with and without streaming.

## Normalizing the Output Format with format

The `format` option normalizes the stream to a single provider interface, so your clients speak one wire format no matter which vendor serves the request. KrakenD translates the client’s request into the vendor’s format, and the vendor’s stream back into the chosen format. For example, you can connect to Gemini, Mistral, or OpenAI and still deliver the stream in Anthropic’s format, letting a single client implementation consume any of them.

| Value                | Behavior                                                            |
|----------------------|---------------------------------------------------------------------|
| *(empty or omitted)* | Default. Clients use the configured vendor’s own format, unchanged. |
| `anthropic`          | Clients use the Anthropic Messages API format.                      |
| `openai`             | Clients use the OpenAI Responses API format.                        |

Set `format` in the provider entry. The following configuration connects to Gemini but serves the Anthropic Messages format:

```json
{
  "$schema": "https://www.krakend.io/schema/krakend.json",
  "version": 4,
  "extra_config": {
    "ai/providers": {
      "providers": [
        {
          "name": "gemini-as-anthropic",
          "provider": "gemini",
          "model": "gemini-2.5-flash",
          "credentials": "xxx",
          "streaming": true,
          "format": "anthropic"
        }
      ]
    }
  },
  "endpoints": [
    {
      "endpoint": "/v1/messages",
      "method": "POST",
      "output_encoding": "streaming",
      "backend": [
        {
          "extra_config": {

            }

```

A client built for the Anthropic Messages API can consume this endpoint unchanged, even though Gemini serves the request. Because the provider streams, KrakenD calls Gemini’s `streamGenerateContent` method automatically. Setting `format` to the vendor’s own format, such as `anthropic` on an Anthropic provider, changes nothing, as the stream is already in that format.

## Streaming with an Inline Vendor Configuration

When the backend uses an [inline vendor block](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/#inline-vendor-configuration) instead of a provider reference, set `format` next to the vendor block, and point `url_pattern` to the vendor’s streaming method yourself:

```json
{
  "endpoint": "/v1/messages",
  "method": "POST",
  "output_encoding": "streaming",
  "backend": [
    {
      "host": ["https://generativelanguage.googleapis.com"],
      "url_pattern": "/v1beta/models/gemini-2.5-flash:streamGenerateContent?alt=sse",
      "extra_config": {
        "ai/llm": {
          "format": "anthropic",
          "gemini": {
            "v1beta": {
              "credentials": "xxx"
            }
          }
        }
      }
    }
  ]
}
```

This backend behaves like the previous example. The `?alt=sse` query string switches Gemini’s own API into streaming mode, while `output_encoding` only controls how KrakenD talks to the client. Each vendor exposes streaming through its own URL:

- **OpenAI**: the same `/v1/responses` endpoint as non-streaming requests.
- **Gemini**: the `streamGenerateContent` method with `?alt=sse` appended, as shown above.
- **Anthropic**: the same `/v1/messages` endpoint as non-streaming requests.
- **Mistral**: the same `/v1/chat/completions` endpoint as non-streaming requests.
- **Bedrock**: the `converse-stream` method instead of `converse`, for example `/model/{model}/converse-stream`, the streaming counterpart of the [Converse API](https://www.krakend.io/docs/enterprise/ai-gateway/bedrock/). Without `format`, KrakenD streams the response with the `eventstream` wire format instead of SSE, which `output_encoding: "streaming"` resolves automatically.
- **Alibaba Cloud**: the same `/compatible-mode/v1/responses` endpoint as non-streaming requests.

Providers of the inventory select these URLs on their own.

# [OpenAI Integration (available in KrakenD Enterprise)](https://www.krakend.io/docs/enterprise/ai-gateway/openai/)

The **OpenAI integration** connects KrakenD to the [OpenAI Responses API](https://platform.openai.com/docs/api-reference/responses) through the `ai/llm` component of the [unified LLM interface](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/). Clients send only the prompt in the [unified request format](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/#request-format), and KrakenD builds the OpenAI payload, authenticates with your credentials, and returns the [unified response](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/#response-format). Use it to offer OpenAI models behind your own API without sharing your credentials with clients. Because clients never see the OpenAI API, you can move them to another model or vendor later without changing a line of their code.

Keep the OpenAI credentials out of the configuration file

Inject the `credentials` through an environment variable with [Flexible Configuration](https://www.krakend.io/docs/enterprise/configuration/flexible-config/) instead of writing them in plain text, and restrict access to the configuration file.

## Declaring OpenAI in the Provider Inventory

The recommended way to connect to OpenAI is to declare it once in the [LLM provider inventory](https://www.krakend.io/docs/enterprise/ai-gateway/provider-inventory/) and reference it by name from every backend that needs it.
```json
{
  "$schema": "https://www.krakend.io/schema/krakend.json",

  "extra_config": {
    "ai/providers": {
      "providers": [
        {
          "name": "gpt",
          "provider": "openai",
          "model": "gpt-5-nano",
          "credentials": "xxx",
          "variables": {
            "max_output_tokens": 500
          }
        }
      ]
    }
  },
  "endpoints": [
    {
      "endpoint": "/openai",
      "method": "POST",
      "backend": [
        {
          "extra_config": {
            "ai/llm": {
              "provider": "gpt"
            }
          }
        }
      ]
    }
  ]
}
```

The backend needs neither `host` nor `url_pattern`, because the inventory knows the OpenAI endpoint. Any other backend, or the [AI Router](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/), can reuse the `gpt` provider by name. Clients call the endpoint like this:

## OpenAI Configuration Options

The provider entry of the inventory and the inline block accept the same `credentials`, `variables`, `input_template`, `output_template`, and `debug` options. KrakenD sends the `credentials` as a bearer token in the `Authorization` header. Keep in mind:

- The inline block requires `variables.model`. In the inventory, `model` is optional and defaults to `gpt-5.4-mini`.
- `truncation` defaults to `disabled`, so OpenAI returns an error instead of silently dropping part of a long conversation.

These are the fields of the inline `openai` block. The keys of its `variables` object are also the ones a provider entry accepts:

\* required fields

##### [`v1`](https://www.krakend.io/docs/enterprise/ai-gateway/openai/#v1 "Click to copy link to v1")

All settings depend on a specific version, as the vendor might change the API over time.

##### [`credentials`](#v1-credentials "Click to copy link to credentials") * string

Your OpenAI API key. You can set it as an environment variable for better security.

##### [`output_template`](#v1-output_template "Click to copy link to output_template") string

A path to a custom [Go template](https://pkg.go.dev/text/template) that sets how the response from OpenAI is transformed before being sent to the client. The default template extracts the text from the first choice returned by OpenAI so in most cases you don’t need to set a custom output template.

The name of the OpenAI model you want to use. The value you provide is passed as is to OpenAI and KrakenD does not prove if the model is currently accepted by the vendor. Check the available models on OpenAI documentation.

What sampling temperature to use, between `0` and `2`. Higher values like `0.8` will make the output more random, while lower values like `0.2` will make it more focused and deterministic.

##### [`top_p`](#variables-top_p "Click to copy link to top_p") number

The nucleus sampling, where the model considers the results of the tokens with top\_p probability mass. So 0.1 means only the tokens comprising the top 10% probability mass are considered.

##### [`truncation`](#variables-truncation "Click to copy link to truncation")

The strategy to use when truncating messages to fit within the model’s context length (, the model will truncate the response to fit the context window by dropping items from the beginning of the conversation.

Possible values are: `"auto"` , `"disabled"`

## Default OpenAI Prompt Templates

KrakenD talks to OpenAI through a pair of default [prompt templates](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/#prompt-templates). Replace either of them with your own [Go template](https://pkg.go.dev/text/template) file through `input_template` or `output_template` when you need a different payload or response. Use the defaults below as the starting point.

### Default Input Template

KrakenD builds the input template when it starts, writing the values of your `variables` into it. It only writes the `temperature`, `top_p`, `max_output_tokens`, and `model` lines when they have a value. With the configuration of the examples above, the payload sent to OpenAI comes from this template:

```go-text-template
{
	"max_output_tokens": 500,
	"model": "gpt-5-nano",
	"stream": false,
	"truncation": "disabled",
	{{ if hasKey .req_body "instructions" }}"instructions": {{ .req_body.instructions | toJson }},{{ end }}
	"input": {{ .req_body.contents | toJson }}
}
```

When you write your own input template, read your values from `.variables`, for example `{{ .variables.temperature }}`, and the extra attributes from `.variables.extra_payload`.

### Default Output Template

The default output template returns the generated text in `ai_gateway_response` and the token count of `usage.total_tokens` in `usage`:

```go-text-template
{
	"ai_gateway_response": [
		{{ if gt (len .resp_body.output) 0 }}
		{
			"contents": [
			{{ range $output := .resp_body.output }}
			{{ if hasKey $output "content" }}
				{{ range $index, $part := $output.content }}
				{{ if $index }},{{ end }}
				{{ $part.text | toJson }}
				{{ end }}
			{{ end }}
			{{ end }}
			]
		}
		{{ end }}
	],
	"usage": "{{ .resp_body.usage.total_tokens }}"
}
```

If your own output template drops the `usage` field, the [token budgets](https://www.krakend.io/docs/enterprise/ai-gateway/budget-control/) can no longer count the tokens of the response.

A map of additional payload attributes you want to use in your custom `input_template` (this payload is not used in the default template). ##### [`max_output_tokens`](#variables-max_output_tokens "Click to copy link to max_output_tokens") integer

Maximum number of tokens that can be generated in the response. A token is approximately four characters. 100 tokens correspond to roughly 60-80 words.

##### [`stop_sequences`](#variables-stop_sequences "Click to copy link to stop_sequences") array of strings

An array of sequences where the model will stop generating further tokens if found. This can be useful to control the length and content of the output.

##### [`temperature`](#variables-temperature "Click to copy link to temperature") number

The temperature is used for sampling during response generation, which occurs when topP and topK are applied. Temperature controls the degree of randomness in token selection. Lower temperatures are good for prompts that require a less open-ended or creative response, while higher temperatures can lead to more diverse or creative results.

##### [`top_k`](#variables-top_k "Click to copy link to top_k") integer

Top-K changes how the model selects tokens for output. A top-K of 1 means the next selected token is the most probable among all tokens in the model’s vocabulary (also called greedy decoding), while a top-K of 3 means that the next token is selected from among the three most probable tokens by using temperature.

##### [`top_p`](#variables-top_p "Click to copy link to top_p") number

Top-P changes how the model selects tokens for output. Tokens are selected from the most probable to least probable until the sum of their probabilities equals the top-P value. For example, if tokens A, B, and C have a probability of 0.3, 0.2, and 0.1 and the top-P value is 0.5, then the model will select either A or B as the next token by using temperature and excludes C as a candidate.

```go-text-template
	"system_instruction": {
		"parts": [
			{
				"text": {{ .req_body.instructions | toJson }}
			}
		]
	},
	{{ end }}
	"contents": [
		{
			"parts": [
				{
					"text": {{ .req_body.contents | toJson }}
				}
			]
		}
	]
}
```

When you write your own input template, read your values from `.variables`, for example `{{ .variables.temperature }}`, and the extra attributes from `.variables.extra_payload`.

### Default Output Template

The default output template returns the generated text in `ai_gateway_response` and the token count of `usageMetadata.totalTokenCount` in `usage`:

```go-text-template
{
	"ai_gateway_response":
	[
		{{ if gt (len .resp_body.candidates) 0 }}
		{
			"contents": [
			{{ range $ci, $candidate := .resp_body.candidates }}
				{{ range $index, $part := $candidate.content.parts }}
				{{ if $ci }},{{ end }}
				{{ $part.text | toJson }}
				{{ end }}
			{{ end }}
			]
		}
		{{ end }}
	],
	"usage": "{{ .resp_body.usageMetadata.totalTokenCount }}"
}
```

If your own output template drops the `usage` field, the [token budgets](https://www.krakend.io/docs/enterprise/ai-gateway/budget-control/) can no longer count the tokens of the response.

A map of additional payload attributes you want to use in your custom `input_template` (this payload is not used in the default template). ##### [`max_tokens`](#variables-max_tokens "Click to copy link to max_tokens") integer

Maximum number of tokens that can be generated in the response. A token is approximately four characters. 100 tokens correspond to roughly 60-80 words.

Defaults to `1024`

##### [`model`](#variables-model "Click to copy link to model") * string

The name of the Anthropic model you want to use.

Examples: `"claude-haiku-4-5"` , `"claude-sonnet-5-5"` , `"claude-opus-5-5"`

##### [`stop_sequences`](#variables-stop_sequences "Click to copy link to stop_sequences") array of strings

An array of sequences where the model will stop generating further tokens if found. This can be useful to control the length and content of the output.

##### [`temperature`](#variables-temperature "Click to copy link to temperature") number

The temperature is used for sampling during response generation, which occurs when topP and topK are applied. Temperature controls the degree of randomness in token selection. Lower temperatures are good for prompts that require a less open-ended or creative response, while higher temperatures can lead to more diverse or creative results. Claude Opus 4.7 and newer models reject requests that set it with a `400` error, so use it only with earlier models such as Claude Sonnet 4.6 or Claude Haiku 4.5.

##### [`top_k`](#variables-top_k "Click to copy link to top_k") integer

Top-K changes how the model selects tokens for output. A top-K of 1 means the next selected token is the most probable among all tokens in the model’s vocabulary (also called greedy decoding), while a top-K of 3 means that the next token is selected from among the three most probable tokens by using temperature. Claude Opus 4.7 and newer models reject requests that set it with a `400` error, so use it only with earlier models such as Claude Sonnet 4.6 or Claude Haiku 4.5.

##### [`top_p`](#variables-top_p "Click to copy link to top_p") number

Top-P changes how the model selects tokens for output. Tokens are selected from the most probable to least probable until the sum of their probabilities equals the top-P value. For example, if tokens A, B, and C have a probability of 0.3, 0.2, and 0.1 and the top-P value is 0.5, then the model will select either A or B as the next token by using temperature and excludes C as a candidate. Claude Opus 4.7 and newer models reject requests that set it with a `400` error, so use it only with earlier models such as Claude Sonnet 4.6 or Claude Haiku 4.5.

```json
        "ai/llm": {
          "bedrock": {
            "v1": {
              "credentials": "xxx",
              "variables": {
                "max_tokens": 500
              }
            }
          }
        }
      }
    }
  ]
}
```

## Amazon Bedrock Configuration Options

The provider entry of the inventory and the inline block accept the same `credentials`, `variables`, `input_template`, `output_template`, and `debug` options. KrakenD sends the `credentials`, a [Bedrock API key](https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys.html), as a bearer token in the `Authorization` header. Keep in mind:

- Bedrock selects the model and the region in the URL, not in the payload. ##### Fields of Bedrock integration

\* required fields

##### [`v1`](https://www.krakend.io/docs/enterprise/ai-gateway/bedrock/#v1 "Click to copy link to v1")

All settings depend on a specific version, as the vendor might change the API over time.

##### [`credentials`](#v1-credentials "Click to copy link to credentials") * string

Your Bedrock API key. You can set it as an environment variable for better security.

##### [`debug`](#v1-debug "Click to copy link to debug") boolean

Enables the debug mode to log activity for troubleshooting. Do not set this value to true in production as it may log sensitive data.

Defaults to `false`

##### [`input_template`](#v1-input_template "Click to copy link to input_template") string

A path to a custom [Go template](https://pkg.go.dev/text/template) that sets the payload format sent to Bedrock. You don’t need to set this value unless you want to override the default template making use of all the `variables` listed in this configuration.

##### [`output_template`](#v1-output_template "Click to copy link to output_template") string

A path to a custom [Go template](https://pkg.go.dev/text/template) that sets how the response from Bedrock is transformed before being sent to the client. The default template extracts the text from the first choice returned by Bedrock so in most cases you don’t need to set a custom output template.

##### [`variables`](#v1-variables "Click to copy link to variables") * object

The variables specific to the Bedrock usage that are used to construct the payload.

##### [`extra_payload`](#variables-extra_payload "Click to copy link to extra_payload") object

A map of additional payload attributes you want to use in your custom `input_template` (this payload is not used in the default template). The attributes set here are accessible in your custom template as `{{ .variables.extra_payload.yourchosenkey }}`. This option helps adding rare customization and future attributes.

##### [`max_tokens`](#variables-max_tokens "Click to copy link to max_tokens") integer

An upper bound for the number of tokens that can be generated for a response, including visible output tokens and reasoning tokens.

##### [`stop_sequences`](#variables-stop_sequences "Click to copy link to stop_sequences") array of strings

An array of sequences where the model will stop generating further tokens if found. This can be useful to control the length and content of the output.

##### [`temperature`](#variables-temperature "Click to copy link to temperature") number

What sampling temperature to use, recommended between 0.0 and 0.7. Higher values like 0.7 will make the output more random, while lower values like 0.2 will make it more focused and deterministic. Change this or top\_p but not both.

##### [`top_k`](#variables-top_k "Click to copy link to top_k") integer

Top-K changes how the model selects tokens for output. A top-K of 1 means the next selected token is the most probable among all tokens in the model’s vocabulary (also called greedy decoding), while a top-K of 3 means that the next token is selected from among the three most probable tokens by using temperature.

##### [`top_p`](#variables-top_p "Click to copy link to top_p") number

A float value between 0 and 1 that controls the nucleus sampling for text generation. It represents the cumulative probability threshold for token selection, where only the most probable tokens that add up to this threshold are considered. A higher value (closer to 1) allows for more diverse outputs, while a lower value (closer to 0) makes the output more focused and deterministic. Change this or temperature but not both.

## Streaming Amazon Bedrock Responses

To forward the tokens as Amazon Bedrock produces them, set the endpoint’s `output_encoding` to `streaming`. When the backend references a provider, also set `streaming` to `true` in the provider entry. Bedrock streams through a different method, `converse-stream`, and uses the binary `eventstream` framing instead of Server-Sent Events. A streaming provider in the inventory switches to it automatically. An inline backend must set it in `url_pattern`, as in `/model/eu.amazon.nova-lite-v1:0/converse-stream`. With `format` set to `openai` or `anthropic`, clients receive Server-Sent Events. [LLM Streaming](https://www.krakend.io/docs/enterprise/ai-gateway/llm-streaming/) explains the `format` option, which presents the stream in the OpenAI or Anthropic format.

## Default Amazon Bedrock Prompt Templates

KrakenD talks to Amazon Bedrock through a pair of default [prompt templates](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/#prompt-templates). Replace either of them with your own [Go template](https://pkg.go.dev/text/template) file through `input_template` or `output_template` when you need a different payload or response. Use the defaults below as the starting point.

### Default Input Template

KrakenD builds the input template when it starts, writing the values of your `variables` into it. It only writes the `maxTokens`, `temperature`, `topP`, and `topK` lines when they have a value. With the configuration of the examples above, the payload sent to Amazon Bedrock comes from this template:

```go-text-template
{
	"inferenceConfig": {
		"maxTokens": 500,
		"stopSequences": []
	},
	{{- if hasKey .req_body "instructions" }}
	"system": [
		{
			"text": {{ .req_body.instructions | toJson }}
		}
	],
	{{ end }}
	"messages": [
		{
			"content": [
				{
					"text": {{ .req_body.contents | toJson }}
				}
			],
			"role": "user"
		}
	]
}
```

When you write your own input template, read your values from `.variables`, for example `{{ .variables.temperature }}`, and the extra attributes from `.variables.extra_payload`.

### Default Output Template

The default output template returns the generated text in `ai_gateway_response` and the token count of `usage.totalTokens` in `usage`:

```go-text-template
{
	"ai_gateway_response":
	[
		{{ if gt (len .resp_body.output.message.content) 0 }}
		{
			"contents": [
			{{ range $ci, $content := .resp_body.output.message.content }}
				{{ if $ci }},{{ end }}
				{{ $content.text | toJson }}
			{{ end }}
			]
		}
		{{ end }}
	],
	"usage": "{{ .resp_body.usage.totalTokens }}"
}
```

If your own output template drops the `usage` field, the [token budgets](https://www.krakend.io/docs/enterprise/ai-gateway/budget-control/) can no longer count the tokens of the response.

# [Other AI Vendors and OpenAI-Compatible Servers (available in KrakenD Enterprise)](https://www.krakend.io/docs/enterprise/ai-gateway/other-vendors/)

KrakenD can connect to **other AI vendors** and self-hosted model servers that have no dedicated integration in the [unified LLM interface](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/). When the server implements the OpenAI Responses API, as Ollama and vLLM do, declare it as an `openai` provider with its own `endpoint` and you get the full unified interface: the same request and response format, token metrics, routing, and streaming. For any other API, write the payload yourself with the request body generator, which works with any vendor at the cost of building and maintaining the templates.

## OpenAI-Compatible Servers

Many vendors and inference servers expose an API compatible with OpenAI. When it implements the [Responses API](https://platform.openai.com/docs/api-reference/responses) (`/v1/responses`), declare it in the [LLM provider inventory](https://www.krakend.io/docs/enterprise/ai-gateway/provider-inventory/) with `provider` set to `openai` and `endpoint` pointing to the server. For example, the following configuration exposes a local Ollama server on `/local`:

```json
{
  "$schema": "https://www.krakend.io/schema/krakend.json",
  "version": 4,
  "extra_config": {
    "ai/providers": {
      "providers": [
        {
          "name": "local-llama",
          "provider": "openai",
          "endpoint": "http://localhost:11434/v1/responses",
          "model": "llama3.2"
        }
      ]
    }
  },
  "endpoints": [
    {
      "endpoint": "/local",
      "method": "POST",
      "backend": [
        {
          "extra_config": {
            "ai/llm": {
              "provider": "local-llama"
            }
          }
        }
      ]
    }
  ]
}
```

KrakenD sends the [OpenAI payload](https://www.krakend.io/docs/enterprise/ai-gateway/openai/#default-input-template) to the Ollama endpoint with the `llama3.2` model, and clients use the [unified request format](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/#request-format):

Send a prompt to a local Ollama server through KrakenD 

```
$curl -XPOST --json '{"contents": "What is an API gateway?"}' http://localhost:8080/local
```

The entry has no `credentials` because a local Ollama server requires none, so KrakenD sends no `Authorization` header. For a server that requires a key, set `credentials` and KrakenD sends it as a bearer token. Because the server is a regular provider, you can reference it from the [AI Router](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/), stream its responses, and enforce [token budgets](https://www.krakend.io/docs/enterprise/ai-gateway/budget-control/) on it like on any other vendor.

Check the Responses API support of your server

Ollama supports `/v1/responses` from version 0.13.3, without its stateful features. vLLM and other servers implement it to different degrees. When your server only offers `/v1/chat/completions`, use the request body generator described below.

## Any Other Vendor API

When the vendor API is not compatible with any supported integration, build the payload yourself. Any AI integration needs two things:

1. The payload format of the vendor endpoint, which the [request body generator](https://www.krakend.io/docs/enterprise/backends/body-generator/) builds from the client request.
2. The vendor authentication, which a [Martian header modifier](https://www.krakend.io/docs/enterprise/backends/martian/#header-modifier) adds to the request.

The following configuration exposes the DeepSeek Chat Completions API on `/deepseek`:

```json
{
  "endpoint": "/deepseek",
  "method": "POST",
  "backend": [
    {
      "host": ["https://api.deepseek.com"],
      "url_pattern": "/chat/completions",
      "extra_config": {
        "modifier/request-body-generator": {
          "path": "/etc/krakend/templates/deepseek.tmpl",
          "content_type": "application/json"
        },
        "modifier/martian": {
          "header.Modifier": {
            "scope": ["request"],
            "name": "Authorization",
            "value": "Bearer YOUR_DEEPSEEK_API_KEY"
          }
        }
      }
    }
  ]
}
```

The `deepseek.tmpl` template builds the Chat Completions payload from the `contents` and `instructions` fields of the client request, the same fields the unified interface uses:

```go-text-template
{
  "model": "deepseek-chat",
  "stream": false,
  "messages": [
    {{- if hasKey .req_body "instructions" }}
    { "role": "system", "content": {{ .req_body.instructions | toJson }} },
    {{- end }}
    { "role": "user", "content": {{ .req_body.contents | toJson }} }
  ]
}
```

The same template works for other servers that implement the Chat Completions API, such as Ollama on `/v1/chat/completions`, after changing the `model`. For a vendor with a different payload, adapt the template to the format of its documentation. Inject the API key through an environment variable with [Flexible Configuration](https://www.krakend.io/docs/enterprise/configuration/flexible-config/) instead of writing it in the configuration.

### Returning the Unified Response

Without more configuration, the endpoint returns the vendor response as is. To give clients the same [unified response](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/#response-format) as the other vendors, add a [response body generator](https://www.krakend.io/docs/enterprise/backends/response-body-generator/) to the backend:

```json
{
  "modifier/response-body-generator": {
    "path": "/etc/krakend/templates/chat-completions-response.tmpl",
    "content_type": "application/json"
  }
}
```

With this template, which reads the first choice of a Chat Completions response:

```go-text-template
{
  "ai_gateway_response": [
    {
      "contents": [
        {{ (index .resp_body.choices 0).message.content | toJson }}
      ]
    }
  ],
  "usage": "{{ .resp_body.usage.total_tokens }}"
}
```

The `usage` field keeps the response compatible with the [token budgets](https://www.krakend.io/docs/enterprise/ai-gateway/budget-control/). This approach does not report the token metrics of the `ai/llm` component, which only covers the supported vendors and the providers of the inventory.

# [Prompt Guard for LLM and Agent Endpoints (available in KrakenD Enterprise)](https://www.krakend.io/docs/enterprise/ai-gateway/prompt-guard/)

**Prompt Guard** inspects the body payload of incoming requests and blocks content that matches known attack patterns, such as prompt injection, jailbreaks, or data exfiltration attempts. It applies one or more *guards* to the request and rejects the call when a guard flags the payload as malicious. Because it operates on the raw request body, you can add it to **any endpoint that accepts a body**, not only to those connected to an LLM backend. KrakenD ships with a set of default guards that block well-known attack phrasings as soon as you enable Prompt Guard, and you can extend or restrict them through configuration.

Security notice

Prompt guards evaluate untrusted user input. The `policy` guard can additionally reference request metadata such as headers, query strings, and the URL. Review which guards you enable per endpoint and keep the default guards active unless you have a specific reason to disable them. The default guards are a first layer of defense, not complete protection: they only detect the phrasings their patterns know.

## How Prompt Guard Works

KrakenD maintains a global shared registry that holds both the default guards and the guards you define in your configuration. When a request reaches a protected endpoint, the gateway selects the guards that apply, combines them into a single guard, and evaluates the request body against it.

Three kinds of guards are available:

- **Regex**: matches the body against a list of regular expressions.
- **Classifier**: sends the body to an external service that returns a score.
- **Policy**: evaluates CEL expressions against the body and request metadata.

The default guards are a large set of regular expressions covering common attack categories. They match known phrasings of each attack, so a request that asks for the same thing in different words gets through. Use them as a fast first layer, and add a [classifier guard](https://www.krakend.io/docs/enterprise/ai-gateway/prompt-guard/#classifier-guards) alongside them when you need detection based on the meaning of the request rather than its wording. KrakenD merges all regex guards (defaults and your own) into a single set so it can test every pattern in one pass, which keeps evaluation fast even when the number of patterns is high.

## Enabling Prompt Guard

Prompt Guard uses the `ai/prompt-guard` namespace in the `extra_config`. The default guards are active on any endpoint or backend where you add the namespace, even with an empty object. To take full control, declare your own guards at the service level and then choose which guards apply on each endpoint or backend.

A configuration has two parts:

1. The **guard definitions**, placed in the root `extra_config`, where you describe each custom guard.
2. The **guard selection**, placed in the `extra_config` of each endpoint or backend, where you list the guards to apply by name.

## Defining Guards

You define each custom guard at the service level inside the `ai/prompt-guard` namespace, under the `guards` list. Every guard declaration has a `name` to reference it, a `kind` (`regex`, `classifier`, or `policy`), a `severity` from `critical` (highest) to `low` (lowest), and a `config` object whose fields depend on the kind.

Severity levels matter when selecting or disabling guards: you can disable all default guards of a given severity (see [Disabling Default Guards](https://www.krakend.io/docs/enterprise/ai-gateway/prompt-guard/#disabling-default-guards)).

The following fields are available at the service level:

##### Fields of AI Prompt Guard

\* required fields

##### [`guards`](https://www.krakend.io/docs/enterprise/ai-gateway/prompt-guard/#guards "Click to copy link to guards") array of objects

The list of custom guards available to endpoints and backends. Each guard has a unique `name`, a `kind` that defines how it evaluates the request, a `severity`, and a `config` whose fields depend on the `kind`.

Each item of guards accepts the following properties:

##### [`config`](#guards-config "Click to copy link to config") * object

The settings of the guard. Its fields depend on the `kind`: `patterns` for a `regex` guard, `url` and `score_threshold` for a `classifier` guard, and `expressions` for a `policy` guard.

##### [`kind`](#guards-kind "Click to copy link to kind") *

How the guard evaluates the request. A `regex` guard matches the body against a list of regular expressions, a `classifier` guard sends the body to an external service that returns a score, and a `policy` guard evaluates CEL expressions against the body and the request metadata.

Possible values are: `"regex"` , `"classifier"` , `"policy"`

##### [`name`](#guards-name "Click to copy link to name") * string

A unique name for this guard. Endpoints and backends reference the guard through this value in their `guards` list.

Examples: `"block_jailbreak_terms"` , `"injection_classifier"`

##### [`severity`](#guards-severity "Click to copy link to severity") *

The severity level assigned to the guard, from `critical` (highest) to `low` (lowest). Endpoints and backends can disable all the default guards of a given severity by adding `!critical`, `!high`, `!medium`, or `!low` to their `guards` list.

Possible values are: `"critical"` , `"high"` , `"medium"` , `"low"`

Schema: [https://www.krakend.io/schema/v3.0/ai/prompt-guard.json](https://www.krakend.io/schema/v3.0/ai/prompt-guard.json "JSON schema definition")

### Regex Guards

A `regex` guard matches the request body against a list of regular expressions. If any pattern matches, the guard blocks the request. Define the patterns under `config.patterns`:

```json
{
  "name": "block_jailbreak_terms",
  "kind": "regex",
  "severity": "high",
  "config": {
    "patterns": [
      "(?i)ignore (all )?previous instructions",
      "(?i)disregard .*(system )?prompt"
    ]
  }
}
```

The guard above blocks any request whose body matches either pattern. KrakenD combines these patterns with the patterns of all other regex guards into a single set evaluated in one pass.

### Classifier Guards

A `classifier` guard delegates the decision to an external service. KrakenD sends the body to the configured `url`, and the service responds with a JSON payload that contains a `score` between `0.0` and `1.0`, both included. A score of `0.0` means “do not block”, and `1.0` is the maximum confidence that the payload should be blocked:

```json
{ "score": 0.23 }
```

You configure a classifier guard with the endpoint to call and the threshold that decides the outcome:

```json
{
  "name": "injection_classifier",
  "kind": "classifier",
  "severity": "high",
  "config": {
    "score_threshold": 0.6,
    "on_failure_block": false,
    "url": "https://example.com/classify"
  }
}
```

The guard blocks the request when the returned score is equal to or greater than `score_threshold`. The `on_failure_block` flag controls the behavior when the external service cannot be reached or returns an error: set it to `true` to block the request on failure, or `false` to let it through.

### Policy Guards

A `policy` guard evaluates a list of CEL `expressions` against the request. The body is exposed as a single `body` **string**, not as parsed JSON. A `meta` object exposes the request context with the same data available to other [Security Policies](https://www.krakend.io/docs/enterprise/security-policies/):

- `headers`
- `params`
- `method`
- `path`
- `query`
- `url`

```json
{
  "name": "payload_policy",
  "kind": "policy",
  "severity": "medium",
  "config": {
    "expressions": [
      "meta.method != 'POST'",
      "size(body) > 8192"
    ]
  }
}
```

The guard blocks the request when any of its expressions evaluates to `true`, so write each expression as a condition to block. The policy above blocks any request that is not a `POST` and any request whose body is larger than 8 KB, so only `POST` requests of 8 KB or less get through. An expression that cannot be evaluated, for example one that reads a `meta` field that does not exist, does not block the request. Use `body` to inspect the raw payload and `meta` to reason about the request headers, parameters, method, path, query string, and URL.

## Selecting Guards per Endpoint or Backend

After defining guards at the service level, add the `ai/prompt-guard` namespace to the endpoint or backend you want to protect, and list the guards to apply by `name`. You can protect either the endpoint or an individual backend.

The following endpoint applies a regex guard and a classifier guard defined earlier:

```json
{
  "endpoint": "/guard/on/endpoint",
  "method": "POST",
  "input_headers": [
    "*"
  ],
  "backend": [
    {
      "url_pattern": "/v1/chat/completions",
      "method": "POST",
      "encoding": "json"
    }
  ],
  "extra_config": {
    "ai/prompt-guard": {
      "guards": [
        "block_jailbreak_terms",
        "injection_classifier"
      ]
    }
  }
}
```

To protect a specific backend instead of the whole endpoint, move the namespace into the backend’s `extra_config`:

```json
{
  "endpoint": "/guard/on/backend",
  "method": "POST",
  "input_headers": [
    "*"
  ],
  "backend": [
    {
      "url_pattern": "/v1/chat/completions",
      "method": "POST",
      "extra_config": {
        "ai/prompt-guard": {
          "guards": [
            "block_jailbreak_terms",
            "injection_classifier"
          ]
        }
      }
    }
  ]
}
```

Both examples keep the default guards active in addition to the named guards you selected. The following fields are available at the endpoint and backend levels:

##### Fields of AI Prompt Guard Selection

\* required fields

##### [`guards`](https://www.krakend.io/docs/enterprise/ai-gateway/prompt-guard/#guards "Click to copy link to guards") array of strings

The guards to apply, in addition to the default ones. Add the `name` of a guard declared at the service level to apply it, or prefix an entry with `!` to disable default guards: `!all_defaults` removes all of them, `!critical`, `!high`, `!medium`, and `!low` remove those of that severity, and `!` followed by a group name, such as `!unicode_steganography`, removes that group.

Schema: [https://www.krakend.io/schema/v3.0/ai/prompt-guard-endpoint.json](https://www.krakend.io/schema/v3.0/ai/prompt-guard-endpoint.json "JSON schema definition")

## Disabling Default Guards

The `guards` list also accepts negations to remove default guards for an endpoint or backend. Prefix the name with an exclamation mark `!` to disable it:

- `!all_defaults`: Removes all default guards. Only the guards you explicitly select remain. If this is the only entry, KrakenD applies an internal no-op guard, effectively disabling Prompt Guard for that endpoint.
- `!low`, `!medium`, `!high`, `!critical`: Disable all default guards of that severity level.
- `!group_name`: Disable a specific default guard group, for example `!unicode_steganography`.

For instance, the following selection applies two named guards while disabling every default guard with `medium` severity and the `unicode_steganography` group:

```json
{
  "ai/prompt-guard": {
    "guards": [
      "block_jailbreak_terms",
      "injection_classifier",
      "!medium",
      "!unicode_steganography"
    ]
  }
}
```

## Prompt Guard Metrics and Traces

When you enable [OpenTelemetry](https://www.krakend.io/docs/enterprise/telemetry/opentelemetry/), Prompt Guard reports the `krakend.promptguard.check` counter, which increases every time a prompt guard runs. On the Prometheus exporter it appears as `krakend_promptguard_check_requests_total`. It carries the following attributes:

- `krakend_promptguard_blocked`: `true` when a guard blocked the request, and `false` when the request passed.
- `http_route`: the endpoint that received the request.
- `krakend_backend`: the `url_pattern` of the backend, when you set Prompt Guard at the backend level. It is empty when you set Prompt Guard at the endpoint level.

The counter does not record which guard blocked the request: blocks by different guards on the same route add up in the same series.

Prompt Guard also adds its result as an attribute of the current trace.

## Complementary Prompt Controls

Prompt Guard detects malicious content, but other KrakenD components restrict what a prompt can be before any guard runs. Combine them on the same endpoint to reduce what reaches your LLMs:

- [JSON Schema validation](https://www.krakend.io/docs/enterprise/endpoints/json-schema/) rejects requests whose body does not follow the structure you expect, such as an unknown field or a prompt longer than a limit.
- The [maximum request size](https://www.krakend.io/docs/enterprise/endpoints/maximum-request-size/#limit-the-maximum-request-size-to-an-endpoint) rejects oversized payloads with a `413` status code before KrakenD reads them.
- [Prompt templates](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/#prompt-templates) fix the system prompt and the vendor payload on the gateway, so clients only provide the content.
- [Rate limits](https://www.krakend.io/docs/enterprise/endpoints/rate-limit/) and [token budgets](https://www.krakend.io/docs/enterprise/ai-gateway/budget-control/) cap how much each user, team, or tenant can send.

The following endpoint applies all of them. It validates the JWT and propagates its `team` claim, limits the body size and structure, runs the default guards, and allows each team ten requests per minute:

```json
{
  "endpoint": "/chat",
  "method": "POST",
  "input_headers": ["X-Team"],
  "extra_config": {
    "auth/validator": {
      "alg": "RS256",
      "jwk_url": "https://idp.example.com/.well-known/jwks.json",
      "cache": true,
      "propagate_claims": [
        ["team", "X-Team"]
      ]
    },
    "proxy": {
      "max_payload": 16384
    },
    "validation/json-schema": {
      "type": "object",
      "required": ["contents"],
      "properties": {
        "contents": {
          "type": "string",
          "maxLength": 4000
        },
        "instructions": {
          "type": "string",
          "maxLength": 1000
        }
      },
      "additionalProperties": false
    },
    "ai/prompt-guard": {},
    "qos/ratelimit/router": {
      "client_max_rate": 10,
      "every": "1m",
      "strategy": "header",
      "key": "X-Team"
    }
  },
  "backend": [
    {
      "extra_config": {
        "ai/llm": {
          "provider": "chat"
        }
      }
    }
  ]
}
```

Requests larger than 16 KB, with fields other than `contents` and `instructions`, or with a prompt longer than 4000 characters never reach the guards. The rate limit counts the requests of each team separately, using the header KrakenD sets from the validated token. The `chat` provider comes from the [LLM provider inventory](https://www.krakend.io/docs/enterprise/ai-gateway/provider-inventory/). For the data that leaves the gateway, see [AI Security](https://www.krakend.io/docs/enterprise/ai-gateway/security/).

# [AI Gateway Security and Data Protection (available in KrakenD Enterprise)](https://www.krakend.io/docs/enterprise/ai-gateway/security/)

**AI Gateway security** is the set of KrakenD controls that protect the traffic between your consumers and the LLM vendors. KrakenD authenticates consumers with your own identity mechanisms, keeps the vendor API keys on the gateway, masks sensitive data in prompts and responses, and restricts what data can leave your perimeter. Use these controls whenever internal or external consumers reach an LLM through KrakenD. Because they live at the gateway, you apply them to every AI endpoint without changing the applications or the vendors.

This page covers authentication, API keys, and data protection. To block prompt injection, jailbreaks, and other malicious payloads before they reach the model, see [Prompt Guard](https://www.krakend.io/docs/enterprise/ai-gateway/prompt-guard/).

## Isolated Authentication

KrakenD separates the authentication of the consumers from the authentication against the LLM vendors. Consumers authenticate with the mechanism of your choice, and only the gateway holds the vendor credentials:

![ai-gateway-isolated-auth.mmd diagram](https://www.krakend.io/images/documentation/diagrams/ai-gateway-isolated-auth.mmd.svg)

Most LLM vendors authenticate with a static API key. Instead of sharing that key with your consumers, demand the credentials of your existing identity provider at the endpoint, for instance with [JWT validation](https://www.krakend.io/docs/enterprise/authorization/jwt-validation/) or [API keys](https://www.krakend.io/docs/enterprise/authentication/api-keys/), and leave the vendor key in the [LLM provider inventory](https://www.krakend.io/docs/enterprise/ai-gateway/provider-inventory/):

```json
{
  "$schema": "https://www.krakend.io/schema/krakend.json",
  "version": 4,
  "extra_config": {
    "ai/providers": {
      "providers": [
        {
          "name": "chat",
          "provider": "openai",
          "model": "gpt-5-nano",
          "credentials": "xxx"
        }
      ]
    }
  },
  "endpoints": [
    {
      "endpoint": "/chat",
      "method": "POST",
      "extra_config": {
        "auth/validator": {
          "alg": "RS256",
          "jwk_url": "https://idp.example.com/.well-known/jwks.json",
          "cache": true
        }
      },
      "backend": [
        {
          "extra_config": {
            "ai/llm": {
              "provider": "chat"
            }
          }
        }
      ]
    }
  ]
}
```

Consumers call `/chat` with a token issued by your identity provider, and KrakenD calls OpenAI with the key of the `chat` provider. The OpenAI key never leaves the gateway, and revoking a consumer does not require rotating it.

## Protecting LLM API Keys

The `credentials` of each provider live in the KrakenD configuration. Keep them out of the file and out of your repositories:

- Inject them from environment variables with [Flexible Configuration](https://www.krakend.io/docs/enterprise/configuration/flexible-config/), writing `"credentials": "{{ env "OPENAI_API_KEY" }}"` in the provider entry.
- Restrict access to the configuration file and to the environment of the KrakenD process.
- Keep `debug` set to `false` in production, as the debug logs may contain sensitive data.

When consumers use the vendor API directly through a `no-op` endpoint, KrakenD does not process the payload, and a Martian header modifier adds the key instead. See [Vendor-Native Passthrough](https://www.krakend.io/docs/enterprise/ai-gateway/llm-routing/#vendor-native-passthrough).

## Data Masking and Data Loss Prevention

**Data masking** replaces sensitive values, such as credit card numbers or personal identifiers, before they leave KrakenD. Apply it to the responses, so consumers and logs never see the raw values, and to the prompts, so consumers cannot send sensitive content to an LLM vendor. KrakenD masks data with the [request and response manipulation components](https://www.krakend.io/docs/enterprise/request-response-manipulation/), using regular expressions on the content.

### Masking Sensitive Data in Responses

The [regular expression modifier](https://www.krakend.io/docs/enterprise/endpoints/content-replacer/#regular-expression-modifier) of the `modifier/response-body` namespace rewrites a field of the response with a regular expression. The following example uses the echo backend to mask the digits in the path of the request, except the last four:

```json
{
  "version": 4,
  "$schema": "https://www.krakend.io/schema/krakend.json",
  "host": [
    "localhost:8080"
  ],
  "echo_endpoint": true,
  "endpoints": [
    {
      "endpoint": "/mask",
      "method": "GET",
      "backend": [
        {
          "url_pattern": "/__echo/123456789",
          "extra_config": {
            "modifier/response-body": {
              "modifiers": [
                {
                  "regexp": {
                    "@comment": "Example of masking SSN or credit numbers in the response body",
                    "field": "req_uri_details.path",
                    "find": "([\\d+\\-\\s]*)(\\d{4})",
                    "replace": "XXX-$2"
                  }
                }
              ]
            }
          }
        }
      ]
    }
  ]
}
```

The `field` attribute selects the element of the response to rewrite, and the `find` expression matches any sequence of digits, hyphens, and spaces followed by four digits, which the `replace` turns into `XXX-` and the last four digits. Stack as many modifiers as you need in the `modifiers` array.

### Masking Sensitive Data in Prompts

To mask the prompt before it reaches the LLM, apply the regular expression in the template that builds the payload. For instance, consider a consumer that sends a number that must never reach the vendor:

Send a prompt that contains sensitive data 

```
$curl -H'Content-Type: application/json' \
  -d '{"message": "123456789 is a number that should never be sent"}' \
  http://localhost:8080/req-mask
```

The [request body generator](https://www.krakend.io/docs/enterprise/backends/body-generator/) builds the payload with a template that masks the number:

```go-text-template
{{- $message := index .req_body "message" -}}
{{- $message = regexReplaceAll "([\\d+\\-\\s]*)(\\d{4})" $message "XXX-${2}" -}}
{
    "message": {{ $message | toJson }}
}
```

The configuration loads the template from `body_mask.tmpl`:

```json
{
  "endpoint": "/req-mask",
  "method": "POST",
  "backend": [
    {
      "url_pattern": "/__echo/test",
      "host": ["http://localhost:8080"],
      "extra_config": {
        "modifier/request-body-generator": {
          "path": "body_mask.tmpl",
          "content_type": "application/json"
        }
      }
    }
  ]
}
```

The backend receives the masked payload:

```json
{
  "message": "XXX-6789 is a number that should never be sent"
}
```

When the backend uses the `ai/llm` component, apply the same `regexReplaceAll` to `.req_body.contents` in a custom [input template](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/#prompt-templates), so the masked prompt goes straight into the vendor payload.

## Exfiltration Prevention

**Exfiltration prevention** restricts, sanitizes, or monitors the data that leaves your perimeter through the gateway, so no unauthorized or sensitive data reaches consumers or LLM vendors. Combine these controls:

- Use an [allow list](https://www.krakend.io/docs/enterprise/backends/data-manipulation/#allow) for APIs that must return a limited set of attributes.
- Use [Security Policies](https://www.krakend.io/docs/enterprise/security-policies/) to check the roles and conditions required to deliver content.
- Use [regular expression masking](https://www.krakend.io/docs/enterprise/ai-gateway/security/#data-masking-and-data-loss-prevention) on the fields that must never leave in full.
- Use [prompt templates](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/#prompt-templates) instead of open LLM queries, so consumers only provide the content.
- Use [Prompt Guard](https://www.krakend.io/docs/enterprise/ai-gateway/prompt-guard/), which includes default guards against data exfiltration attempts.
- Write custom logic in [request and response modifier plugins](https://www.krakend.io/docs/enterprise/extending/plugin-modifiers/) when the rules above are not enough.

# [LLM Token Budgets with Quotas (available in KrakenD Enterprise)](https://www.krakend.io/docs/enterprise/ai-gateway/budget-control/)

A **token budget** caps how many LLM tokens a user, plan, or tenant can consume in a period of time, such as 100,000 tokens per day. KrakenD enforces it with the [Quota](https://www.krakend.io/docs/enterprise/governance/quota/) component: instead of counting one hit per request, the quota reads the number of tokens from each LLM response and adds it to a persistent counter in Redis. Use it to contain the spend of your AI endpoints, to sell plans with different allowances, or to share a vendor contract between teams. Because the counter lives in Redis, the budget holds across every KrakenD instance of your cluster.

## How Token Budgets Work

A token budget combines three pieces of the quota configuration:

1. A Redis connection pool, where KrakenD stores the counters.
2. A quota **processor** under `governance/processors`, with one rule per plan and the token limits of each rule, per hour, day, week, month, or year.
3. A `governance/quota` attached to the endpoint, which identifies the user and the plan of each request and reads the tokens from the response with `weight_strategy` set to `body` and `weight_key` pointing to the token count.

Before calling the LLM, KrakenD checks the counter of the user. When the counter has reached a limit, the client gets a `429` status code with a `Retry-After` header, and the LLM is not called. Otherwise, KrakenD calls the LLM and, once the response arrives, adds its tokens to the counter. A call that starts under the limit always completes, even when its tokens take the counter above the limit; the next call of that user is the one rejected.

## Token Budget for LLM Responses

The [unified response](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/#response-format) of the `ai/llm` component carries the total tokens of the call in its `usage` field, whatever the vendor or provider behind the endpoint. Point `weight_key` to `usage` to count them. The quota reads the value although it is a string.

The following configuration gives `pro` users 500,000 tokens per day and everyone else 50,000. The JWT carries the plan and the user identifier, which KrakenD propagates as headers for the quota to read:


## Token Budget for Streaming Responses

When the endpoint streams the response, the quota reads every event of the stream and adds the weight of each event that carries the `weight_key`. Choose a key that appears in a single event, so each call counts once.

## Reducing the Token Spend

A budget caps the spend, while other KrakenD features reduce it:

- The [Semantic Cache](https://www.krakend.io/docs/enterprise/ai-gateway/semantic-cache/) returns a stored response when a new prompt means the same as a previous one, without calling the LLM.
- The [AI Router](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/) sends each request to the cheapest provider that fits it, by plan, use case, or with a classifier.
- [Prompt controls](https://www.krakend.io/docs/enterprise/ai-gateway/prompt-guard/#complementary-prompt-controls) limit the size of the prompts and the rate of requests before they consume tokens.

To follow the token consumption per provider and model in your observability stack, see [AI Monitoring](https://www.krakend.io/docs/enterprise/ai-gateway/usage-monitoring/).

# [Semantic Cache for LLM and Agent Responses (available in KrakenD Enterprise)](https://www.krakend.io/docs/enterprise/ai-gateway/semantic-cache/)

The **semantic cache** stores responses keyed by the meaning of the request rather than by an exact match. KrakenD turns the request content into an embedding vector and, when a new request is close enough in meaning to one it has already seen, returns the stored response instead of calling the backend again. Use it in front of LLMs and agents, where users phrase the same question in many different ways and every call costs tokens and time. The result is lower token spend and latency, and you can enable it on any endpoint or backend.

Not the same as HTTP response caching

The semantic cache matches requests by meaning. It is different from the [backend response caching](https://www.krakend.io/docs/enterprise/backends/caching/) (`qos/http-cache`), which caches backend responses verbatim based on HTTP cache headers. Use response caching for identical, cacheable HTTP responses, and the semantic cache for paraphrased requests to AI backends.

## How the Semantic Cache Works

For each request, KrakenD takes the content you choose with `req_content` and converts it into a vector using an **embedder** (an ONNX model). It then queries Redis for the nearest stored vector. When the cosine distance between the incoming vector and a stored one is within `max_distance`, KrakenD treats it as a hit and returns the cached response without contacting the backend. When no stored vector is close enough, it is a miss: KrakenD calls the backend, returns the response, and stores it together with its vector for future requests.

A `max_distance` of `0` only matches identical vectors. A lower value requires requests to be more similar before they match, so it produces fewer but more precise hits. A higher value returns more hits at the risk of matching less related requests.

The semantic cache needs three things in place: an embedding model in ONNX format, a Redis connection to store the vectors and responses, and an embedder definition that links the two. You can optionally add OpenTelemetry to collect hit and miss metrics.

With Docker, mount a host directory on `/etc/krakend/models` so the model stays on your host after the container exits. ```

The container downloads the default model and writes it to the `models` directory on your host, inside the `sentence-transformers_all-MiniLM-L6-v2` subfolder. When the download finishes, the command prints:

```log

```

### Model Download Cache Directory

The `download-model` command first downloads the model files into a cache directory, and then copies them to the `--path` directory. By default, the cache is a temporary directory under the operating system’s temp folder (`$TMPDIR`, or `/tmp` on Linux) that the command deletes when it finishes. As a result, every run downloads the full model again (about 87 MiB for the default model) and copies it to `--path` again, even when `--path` already contains it.

To keep the downloaded files between runs, set `--cache-dir` to a persistent directory. When the model is already in the cache, the command reuses it and does not use the network at all. With Docker, mount a host directory for the cache. As with the models directory, both directories must exist and be writable by UID `1000`:

Reusing the download cache between runs 

```
$mkdir -p models hf-cache
docker run --rm \
  -v "$PWD/hf-cache:/cache" \
  -v "$PWD/models:/etc/krakend/models" \
  krakend/krakend-ee:3.0 ai download-model --cache-dir /cache
```

The first run downloads the model into `hf-cache` and copies it to `models`. Later runs find the files in `hf-cache` and skip the download. Every run ends with the same message:

```log
OK: model successfully downloaded to:   /etc/krakend/models/sentence-transformers_all-MiniLM-L6-v2
```

Cache location before v3.0.4

Versions before v3.0.4 do not have the `--cache-dir` and `--timeout` flags. They always cache the download in `$XDG_CACHE_HOME/huggingface/hub`, or in `$HOME/.cache/huggingface/hub` when `XDG_CACHE_HOME` is not set. The official Docker image runs as the `krakend` user, which has no home directory, so the download fails with a `permission denied` error. Set `XDG_CACHE_HOME` to a writable directory to work around it. The `models` directory must also be writable by UID `1000`:

Downloading a model with v3.0.3 or earlier 

```
$mkdir -p models
docker run --rm -e XDG_CACHE_HOME=/tmp/cache -v "$PWD/models:/etc/krakend/models" krakend/krakend-ee:3.0.3 ai download-model
```

Declare the shared resources in the root `extra_config`. You need a [Redis connection pool](https://www.krakend.io/docs/enterprise/service-settings/redis-connection-pools/), which the semantic cache uses as its vector storage, and the embedders under the `ai/semantic-cache` namespace. The optional [OpenTelemetry](https://www.krakend.io/docs/enterprise/telemetry/opentelemetry/) block below exposes the cache hit and miss metrics through the [Prometheus](https://www.krakend.io/docs/enterprise/telemetry/prometheus/) exporter:

```json
{
  "$schema": "https://www.krakend.io/schema/krakend.json",
  "version": 4,
  "extra_config": {
    "redis": {
      "connection_pools": [
        {
          "name": "default",
          "address": "localhost:6379"
        }
      ]
    },
    "ai/semantic-cache": {
      "embedders": [
        {
          "name": "default",
          "model_path": "/etc/krakend/models/sentence-transformers_all-MiniLM-L6-v2",
          "vector_dimension": 384
        }
      ]
    },
    "telemetry/opentelemetry": {
      "service_name": "krakend_prometheus_service",
      "metric_reporting_period": 1,
      "trace_sample_rate": 1,
      "exporters": {
        "prometheus": [
          {
            "name": "local_prometheus",
            "port": 9090,
            "process_metrics": true,
            "go_metrics": true
          }
        ]
      }
    }
  }
}
```

The configuration above defines a `default` Redis connection and a `default` embedder pointing to a downloaded model. Endpoints and backends reference these resources by name. The `vector_dimension` must match the output of the model, for example `384` for `all-MiniLM-L6-v2`.

## Enabling the Cache on Endpoints and Backends

Add the `ai/semantic-cache` namespace to the `extra_config` of the endpoint or backend you want to cache. Every field is optional, so the minimum valid configuration is an empty object, which uses the `default` Redis connection, the `default` embedder, and the default distance and TTL:

```json
{
  "extra_config": {
    "ai/semantic-cache": {}
  }
}
```

The following endpoint caches requests using the prompt in the body, scopes the cache per path parameter, and keeps entries for five minutes:

```json
{
  "endpoint": "/1/{ids}",
  "input_headers": ["x-user"],
  "input_query_strings": ["*"],
  "method": "POST",
  "extra_config": {
    "ai/semantic-cache": {
      "redis_connection": "default",
      "embedder": "default",
      "max_distance": 0.15,
      "req_content": "req_body.prompt",
      "key_variants": [
        "req_params.Ids"
      ],
      "ttl": "300s"
    }
  },
  "backend": [
    {
      "url_pattern": "/__echo/1/{ids}"
    }
  ]
}
```

This configuration uses the `default` Redis connection and embedder, vectorizes only the `prompt` field of the request body, and treats vectors within a cosine distance of `0.15` as a match. It also keys the cache on the `Ids` path parameter through `key_variants`, and expires entries after `300s`.

You can place the same configuration in a backend’s `extra_config` instead of the endpoint’s, to cache a single backend within the endpoint:

```json
{
  "endpoint": "/3/{ids}",
  "input_headers": ["x-user"],
  "input_query_strings": ["*"],
  "method": "POST",
  "backend": [
    {
      "url_pattern": "/__echo/3/{ids}",
      "extra_config": {
        "ai/semantic-cache": {
          "redis_connection": "default",
          "embedder": "default",
          "max_distance": 0.15,
          "req_content": "req_params.Ids",
          "key_variants": [
            "req_headers.x-user"
          ],
          "ttl": "300s"
        }
      }
    }
  ]
}
```

These are the configuration options at the endpoint and backend levels:

##### Fields of AI Semantic Cache

\* required fields

##### [`embedder`](https://www.krakend.io/docs/enterprise/ai-gateway/semantic-cache/#embedder "Click to copy link to embedder") string

The name of the embedder to use, as defined in service extra\_config

Defaults to `"default"`

##### [`key_variants`](https://www.krakend.io/docs/enterprise/ai-gateway/semantic-cache/#key_variants "Click to copy link to key_variants") array of strings

Request fields used to create distinct cache entries. Requests with different values for these fields are stored and matched separately, even when their vectorized content is identical.

##### [`max_distance`](https://www.krakend.io/docs/enterprise/ai-gateway/semantic-cache/#max_distance "Click to copy link to max_distance") number

The maximum cosine distance allowed when searching for semantically similar vectors. A value of 0 represents identical vectors; larger values allow greater differences.

Defaults to `0.25`

##### [`redis_connection`](https://www.krakend.io/docs/enterprise/ai-gateway/semantic-cache/#redis_connection "Click to copy link to redis_connection") string

The name of the [Redis connection](https://www.krakend.io/docs/enterprise/service-settings/redis-connection-pools/) to use, it must exist under the `redis` namespace at the service level and written exactly as declared.

Defaults to `"default"`

##### [`req_content`](https://www.krakend.io/docs/enterprise/ai-gateway/semantic-cache/#req_content "Click to copy link to req_content") string

The part of the request to vectorize. Use this to focus semantic matching on the content that can vary between requests. For example, if requests contain a large system prompt shared across calls, you can select only the user prompt to focus vector search on the variable content. If not specified, the entire request body is vectorized.

Examples: `"req_params.Ids"` , `"req_headers.x-user"` , `"req_query_string.user"` , `"req_body.content.prompt"`

##### [`ttl`](https://www.krakend.io/docs/enterprise/ai-gateway/semantic-cache/#ttl "Click to copy link to ttl") string

The time-to-live (TTL) for cached entries.

Specify units using `ns` (nanoseconds), `us` or `µs` (microseconds), `ms` (milliseconds), `s` (seconds), `m` (minutes), or `h` (hours).

Defaults to `"600s"`

Schema: [https://www.krakend.io/schema/v3.0/ai/semantic-cache.json](https://www.krakend.io/schema/v3.0/ai/semantic-cache.json "JSON schema definition")

## Selecting the Content to Match

The `req_content` field decides what KrakenD vectorizes. Use it to focus the matching on the content that varies between requests: for example, if every request carries a large shared system prompt, select only the user prompt. By default it uses the full `req_body`, but you can point it at any of the request input sources:

- `req_body`: the request body. Use [dot-notation](https://www.krakend.io/docs/enterprise/endpoints/request-body-extractor/) to reach nested fields, for example `req_body.content.prompt`.
- `req_params`: a URL path parameter. The key is capitalized, so the endpoint `/1/{ids}` exposes its parameter as `req_params.Ids`.
- `req_query_string`: a query string value, for example `req_query_string.user`.
- `req_headers`: a request header, for example `req_headers.x-user`.

The `key_variants` field takes a list of selectors and uses them to partition the cache. Requests with different values for these fields are stored and matched separately, even when their vectorized content is identical, which lets you keep separate cache entries per user, tenant, or any other dimension. Unlike `req_content`, `key_variants` reads only from `req_params`, `req_query_string`, and `req_headers`; it does not support `req_body`. For example, caching per user with the `x-user` header:

```json
{
  "extra_config": {
    "ai/semantic-cache": {
      "req_content": "req_body.prompt",
      "key_variants": [
        "req_headers.x-user"
      ],
      "ttl": "300s"
    }
  }
}
```

## Sharing Cache Between Endpoints and Backends

Different endpoints never share cache between them. No configuration option enables it.

The same backend shared across different endpoints shares its cache when the HTTP method, host, and URL match, the vector dimension and key variants are the same, and the encoding is compatible.

## Hit and Miss Metrics

When you configure [OpenTelemetry](https://www.krakend.io/docs/enterprise/telemetry/opentelemetry/), the semantic cache reports cache hit and miss metrics. Export them through the [Prometheus](https://www.krakend.io/docs/enterprise/telemetry/prometheus/) exporter, as shown in the service configuration above, to monitor the cache effectiveness and tune `max_distance` and `ttl`.

# [AI Gateway Monitoring with OpenTelemetry (available in KrakenD Enterprise)](https://www.krakend.io/docs/enterprise/ai-gateway/usage-monitoring/)

**AI Gateway monitoring** uses KrakenD’s [OpenTelemetry](https://www.krakend.io/docs/enterprise/telemetry/opentelemetry/) integration to report what your AI traffic consumes and how it behaves. On top of the request, latency, and error metrics KrakenD reports for every backend, the `ai/llm` component counts the input, output, and total tokens of every LLM call, tagged with the provider and the model. Use these metrics to follow the spend of each model, to compare vendors, and to detect consumption spikes in the observability stack you already have. You only need the `telemetry/opentelemetry` namespace: the AI metrics appear as soon as an exporter is configured.

## LLM Token Metrics

Every backend that uses the `ai/llm` component, either with an inline vendor block, with a reference to the [provider inventory](https://www.krakend.io/docs/enterprise/ai-gateway/provider-inventory/), or through the [AI Router](https://www.krakend.io/docs/enterprise/ai-gateway/ai-router/), reports three counters:

| OpenTelemetry metric       | Prometheus metric              | Content                              |
|----------------------------|--------------------------------|--------------------------------------|
| `krakend.llm.tokens-in`    | `krakend_llm_tokens_in_total`  | Input tokens of the prompt           |
| `krakend.llm.tokens-out`   | `krakend_llm_tokens_out_total` | Output tokens generated by the model |
| `krakend.llm.tokens-total` | `krakend_llm_tokens_total`     | Input plus output tokens             |

Each counter carries two attributes:

- `provider`: the vendor that served the request, such as `openai`, `gemini`, `anthropic`, `mistral`, `bedrock`, or `alibaba`.
- `model`: the model that served the request, such as `gpt-5-nano`.

KrakenD reads the token counts from the vendor response before the output template transforms it, so custom [prompt templates](https://www.krakend.io/docs/enterprise/ai-gateway/unified-llm-interface/#prompt-templates) do not change the metrics. With [LLM streaming](https://www.krakend.io/docs/enterprise/ai-gateway/llm-streaming/), KrakenD adds up the tokens reported in the stream and records them when the stream ends.

For example, after two calls of 30 tokens each to a `gpt-5-nano` provider, the Prometheus exporter shows:

```log
krakend_llm_tokens_in_total{model="gpt-5-nano",provider="openai"} 22
krakend_llm_tokens_out_total{model="gpt-5-nano",provider="openai"} 38
krakend_llm_tokens_total{model="gpt-5-nano",provider="openai"} 60
```

The exporter also adds the `otel_scope_*` labels it adds to every KrakenD metric, omitted here for brevity.

## LLM Traces

When you export traces, every call of the `ai/llm` component creates a `krakend-llm` span. When the call ends, the span receives the token counts as attributes, so you can see the cost of each request next to its latency:

- `krakend.llm.tokens-in`, `krakend.llm.tokens-out`, and `krakend.llm.tokens-total`: the tokens of the call.
- `provider`: the vendor that served it.

## Other AI Metrics

Other AI Gateway components report their own metrics through the same exporters:

- [Prompt Guard](https://www.krakend.io/docs/enterprise/ai-gateway/prompt-guard/#prompt-guard-metrics-and-traces) counts every guard evaluation in `krakend_promptguard_check_requests_total`, with an attribute that tells whether the request was blocked.
- The [Semantic Cache](https://www.krakend.io/docs/enterprise/ai-gateway/semantic-cache/#hit-and-miss-metrics) reports its hits and misses, which help you tune its `max_distance` and `ttl`.

## Exporting the AI Metrics

Add the `telemetry/opentelemetry` namespace to the root `extra_config` with the exporters of your observability stack. The following configuration exposes the metrics for [Prometheus](https://www.krakend.io/docs/enterprise/telemetry/prometheus/) on port `9090` and sends the traces to an OpenTelemetry collector through [OTLP](https://www.krakend.io/docs/enterprise/telemetry/opentelemetry/):

```json
{
  "$schema": "https://www.krakend.io/schema/krakend.json",
  "version": 4,
  "extra_config": {
    "telemetry/opentelemetry": {
      "service_name": "ai_gateway",
      "metric_reporting_period": 1,
      "trace_sample_rate": 1,
      "exporters": {
        "prometheus": [
          {
            "name": "local_prometheus",
            "port": 9090
          }
        ],
        "otlp": [
          {
            "name": "local_collector",
            "host": "localhost",
            "port": 4317,
            "use_http": false,
            "disable_metrics": true
          }
        ]
      }
    }
  }
}
```

The Prometheus exporter serves the metrics on `http://localhost:9090/metrics`, and the OTLP exporter only sends the traces, as `disable_metrics` is `true`. Lower `trace_sample_rate` in production to trace a fraction of the requests.

## Querying the Token Consumption

With the metrics in Prometheus, PromQL answers the usual cost questions. For instance, the tokens consumed per model in the last 24 hours:

```text
sum by (model) (increase(krakend_llm_tokens_total[24h]))
```

And the output tokens per second of each vendor, to spot a consumption spike as it happens:

```text
sum by (provider) (rate(krakend_llm_tokens_out_total[5m]))
```

Multiply these values by the price per token of each model to estimate the spend. To limit the consumption instead of observing it, see [Token Budgets](https://www.krakend.io/docs/enterprise/ai-gateway/budget-control/).

# [MCP Gateway for Third-Party MCP Servers (available in KrakenD Enterprise)](https://www.krakend.io/docs/enterprise/ai-gateway/mcp-gateway/)

The **MCP Gateway** is a KrakenD setup that places a third-party Model Context Protocol (MCP) server behind the gateway, so **MCP agents** connect to KrakenD instead of connecting to the server directly. KrakenD relays the MCP messages unchanged through `no-op` endpoints, and adds on the way the controls the server lacks, such as authorization, rate limits, IP filtering, and telemetry. Use it when your agents consume MCP servers that you do not control, or that lack enterprise-ready security and observability. Because KrakenD does not touch the MCP payload, the protocol keeps working end to end, whatever tools the server exposes.

To expose your own APIs and services as MCP tools instead, use the [MCP Server](https://www.krakend.io/docs/enterprise/ai-gateway/mcp-server/), which KrakenD implements natively.

## How the MCP Gateway Works

An MCP server that uses an HTTP transport, such as Streamable HTTP or Server-Sent Events (SSE), receives MCP messages through `POST` requests, opens server-to-client streams through `GET` requests, and ends sessions through `DELETE` requests. The MCP Gateway declares one KrakenD endpoint per method on the same path, all of them with the `no-op` encoding, so KrakenD forwards every message and every stream as is.

Each endpoint is a regular KrakenD endpoint, so you can add to it any component compatible with `no-op`, from [JWT validation](https://www.krakend.io/docs/enterprise/authorization/jwt-validation/) to [rate limits](https://www.krakend.io/docs/enterprise/endpoints/rate-limit/), and the controls apply to every MCP message that goes through.

## Configuring the MCP Gateway

The following configuration relays the MCP traffic of `/mcp` to a third-party MCP server:

```json
{
  "$schema": "https://www.krakend.io/schema/krakend.json",
  "version": 4,
  "endpoints": [
    {
      "endpoint": "/mcp",
      "method": "POST",
      "output_encoding": "no-op",
      "input_headers": [
        "Mcp-Session-Id",
        "Mcp-Protocol-Version"
      ],
      "backend": [
        {
          "host": ["https://mcp.example.com"],
          "url_pattern": "/mcp"
        }
      ]
    },
    {
      "endpoint": "/mcp",
      "method": "GET",
      "output_encoding": "no-op",
      "timeout": "5m",
      "input_headers": [
        "Mcp-Session-Id",
        "Mcp-Protocol-Version"
      ],
      "backend": [
        {
          "host": ["https://mcp.example.com"],
          "url_pattern": "/mcp"
        }
      ]
    },
    {
      "endpoint": "/mcp",
      "method": "DELETE",
      "output_encoding": "no-op",
      "input_headers": [
        "Mcp-Session-Id",
        "Mcp-Protocol-Version"
      ],
      "backend": [
        {
          "host": ["https://mcp.example.com"],
          "url_pattern": "/mcp"
        }
      ]
    }
  ]
}
```

These are the settings that make it work:

- `endpoint`: the path MCP agents connect to. It can be any path, and it does not need to match the path of the MCP server.
- `method`: one endpoint for each of `POST`, `GET`, and `DELETE`. `POST` carries the MCP messages, `GET` opens the server stream, and `DELETE` ends the session.
- `output_encoding`: `no-op` forwards the requests and the responses, including streams, without parsing them.
- `input_headers`: the headers the MCP server needs. The `Mcp-Session-Id` and `Mcp-Protocol-Version` headers of the MCP transport keep the session and the protocol version across requests; add any other header your server requires, such as an `Authorization` header with the client credentials.
- `timeout`: a long timeout on the `GET` endpoint, so KrakenD does not close the server stream while it waits for events.
- `host` and `url_pattern`: the address of the MCP server.

When the MCP server needs an API key that agents must not know, leave it out of `input_headers` and add it on the gateway with a [Martian header modifier](https://www.krakend.io/docs/enterprise/backends/martian/#header-modifier).

## Adding Security and Traffic Controls

Add the components you need to each endpoint of the MCP Gateway. For instance, the following `POST` endpoint demands a valid JWT and allows each client IP sixty MCP messages per minute:

```json
{
  "endpoint": "/mcp",
  "method": "POST",
  "output_encoding": "no-op",
  "input_headers": [
    "Mcp-Session-Id",
    "Mcp-Protocol-Version"
  ],
  "extra_config": {
    "auth/validator": {
      "alg": "RS256",
      "jwk_url": "https://idp.example.com/.well-known/jwks.json",
      "cache": true
    },
    "qos/ratelimit/router": {
      "client_max_rate": 60,
      "every": "1m",
      "strategy": "ip"
    }
  },
  "backend": [
    {
      "host": ["https://mcp.example.com"],
      "url_pattern": "/mcp"
    }
  ]
}
```

Apply the same components to the `GET` and `DELETE` endpoints, so every MCP request goes through them. MCP clients discover how to obtain a token through the OAuth 2.0 Protected Resource Metadata, which KrakenD can serve as explained in [MCP Server Authorization with OAuth](https://www.krakend.io/docs/enterprise/ai-gateway/mcp-server/#mcp-server-authorization-with-oauth).

Other components that fit the MCP Gateway:

- [IP filtering](https://www.krakend.io/docs/enterprise/throttling/ipfilter/) to accept MCP traffic only from known networks.
- [Security Policies](https://www.krakend.io/docs/enterprise/security-policies/) or [CEL expressions](https://www.krakend.io/docs/enterprise/endpoints/common-expression-language-cel/) to apply business rules to each request.
- The [maximum request size](https://www.krakend.io/docs/enterprise/endpoints/maximum-request-size/#limit-the-maximum-request-size-to-an-endpoint) to reject oversized messages.
- [CORS](https://www.krakend.io/docs/enterprise/service-settings/cors/) when browser-based agents connect to the gateway.
- [Telemetry](https://www.krakend.io/docs/enterprise/telemetry/) to trace and measure the MCP traffic of every agent.

# [MCP Server (available in KrakenD Enterprise)](https://www.krakend.io/docs/enterprise/ai-gateway/mcp-server/)

The MCP Server feature **exposes any of your existing use cases as MCP tools** so you can allow to **AI MCP Agents to access any of the systems you have already**, or create new ones easily, whether it is based on legacy services and data or not.

With the MCP Server of KrakenD, you instantly add MCP to all your stack regardless of their native MCP compatibility or not. This unlocks effortless AI-driven integrations by bridging any service with MCP through declarative configuration.

![ai-gateway-mcp-server.mmd diagram](https://www.krakend.io/images/documentation/diagrams/ai-gateway-mcp-server.mmd.svg)

As KrakenD can expose through MCP any kind of service, you can start offering **endless use cases**, and is a game changer to start publishing AI services inside enterprise architectures with no effort.

The key concepts of the MCP server are:

- **Build on-the-fly MCP servers**: Declare and run MCP servers that fetch and send data from and to multiple places.
- **Protocol translation**: Offer MCP, consume anything. E.g., connect to a SOAP service and offer it to Claude via MCP.
- **KrakenD ecosystem compatibility**: MCP servers are first-class citizens and enjoy authorization, throttling, data modification, validation, caching, monitoring, workflows and everything else on KrakenD.
- **Declarative simplicity**: Minimal config additions get powerful AI-optimized APIs in front of any service.
- **Multi-tool support**: Expose multiple AI tools with individual input/output JSON schemas and workflows per MCP server, including mediatypes like audio and images.
- **Stateless or stateful operations**: Choose behavior to align with backend semantics, **SSE available** too.

## MCP Server configuration overview

To start serving MCP on KrakenD, two main configuration sections define MCP Servers:

1. **MCP server declaration** (root `extra_config` with `ai/mcp`)
2. **MCP entrypoint configuration** (endpoint’s `extra_config` with `ai/mcp`)

## MCP Server Authorization with OAuth

The **MCP authorization** protects your MCP servers with the OAuth 2.1 flow that the [MCP specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) defines, so only authenticated AI agents can list and call your tools. In this flow, KrakenD acts as the resource server: it validates the access token of every MCP request and announces which authorization server issues those tokens. Your existing identity provider (Keycloak, Auth0, Okta, or any other OAuth 2.1 server) keeps the user login and the token issuing.

You don’t need any custom code to make it work. Two built-in features of KrakenD Enterprise cover the whole resource server role:

1. The [JWT validation](https://www.krakend.io/docs/enterprise/authorization/jwt-validation/) on the MCP entrypoint rejects requests without a valid token.
2. The [static filesystem](https://www.krakend.io/docs/enterprise/endpoints/serve-static-content/) serves the OAuth 2.0 Protected Resource Metadata ([RFC 9728](https://datatracker.ietf.org/doc/html/rfc9728)), the document MCP clients read to discover your authorization server.

MCP authorization requires HTTPS

MCP clients only complete the OAuth flow against HTTPS URLs, both for the MCP server and the authorization server. Enable [TLS](https://www.krakend.io/docs/enterprise/service-settings/tls/) in KrakenD, or terminate TLS in a load balancer or reverse proxy in front of it, and use the public HTTPS URLs in the metadata document.

The following diagram shows how an MCP client connects to a protected MCP server for the first time:

![ai-gateway-mcp-auth.seq.mmd diagram](https://www.krakend.io/images/documentation/diagrams/ai-gateway-mcp-auth.seq.mmd.svg)

The client sends a first request without a token and receives a `401 Unauthorized`. Then it fetches the metadata document from a well-known URL, learns the authorization server, and completes the login there. From then on, it sends the access token in the `Authorization: Bearer` header of every MCP request, and KrakenD validates it before running any tool.

### Protecting the MCP Entrypoint with JWT Validation

To require a token, add the `auth/validator` namespace to the endpoint that serves as the MCP entrypoint. For example, the following configuration protects the `/mcp` endpoint with the tokens issued by a Keycloak realm, and only accepts users with the `mcp-user` role:

```json
{
  "$schema": "https://www.krakend.io/schema/v3.0/krakend.json",
  "version": 4,
  "extra_config": {
    "ai/mcp": {
      "servers": [
        {
          "name": "store-tools",
          "title": "Store tools",
          "version": "1.0.0",
          "instructions": "Provides tools to check the status of the store",
          "tools": [
            {
              "name": "store-status",
              "title": "Store status",
              "description": "Returns the current status of the store",
              "workflow": {
                "endpoint": "/__mcp/store-status",
                "backend": [
                  {
                    "host": ["https://api.example.com"],
                    "url_pattern": "/status"
                  }
                ]
              }
            }
          ]
        }
      ]
    }
  },
  "endpoints": [
    {
      "endpoint": "/mcp",
      "method": "POST",
      "timeout": "10s",
      "backend": [
        {
          "url_pattern": "/ignore",
          "host": ["ignore"]
        }
      ],
      "extra_config": {
        "ai/mcp": {
          "server_name": "store-tools"
        },
        "auth/validator": {
          "alg": "RS256",
          "jwk_url": "https://idp.example.com/realms/krakend/protocol/openid-connect/certs",
          "issuer": "https://idp.example.com/realms/krakend",
          "audience": ["https://mcp.example.com/mcp"],
          "roles_key": "realm_access.roles",
          "roles_key_is_nested": true,
          "roles": ["mcp-user"]
        }
      }
    }
  ]
}
```

KrakenD checks the signature of the token against the `jwk_url` of your identity provider, its issuer, its audience, and its roles. Requests with a missing, expired, or invalid token get a `401 Unauthorized`, which is the response that starts the OAuth flow on the MCP client. Valid tokens that lack the `mcp-user` role get a `403 Forbidden`.

The MCP specification requires the MCP server to accept only the tokens issued for it, so set the `audience` to the public URL of your MCP endpoint and configure your identity provider to include it in the `aud` claim. This prevents agents from reusing tokens issued for other services. You can combine this validation with the [tool filtering](https://www.krakend.io/docs/enterprise/ai-gateway/mcp-server/#mcp-tool-filtering-by-audience) below, for instance by [propagating a claim](https://www.krakend.io/docs/enterprise/authorization/jwt-validation/#propagate-jwt-claims-as-request-headers) as the header that sets the audience of the tools.

### Announcing the Authorization Server with Protected Resource Metadata

MCP clients need to know which authorization server issues the tokens for your MCP server. The specification offers two discovery mechanisms, a `resource_metadata` parameter in the `WWW-Authenticate` header of the `401` response, or a document served on a well-known URL. MCP clients must support both, so serving the well-known URL is enough.

The well-known URL inserts `/.well-known/oauth-protected-resource` before the path of the MCP endpoint. For an MCP server on `https://mcp.example.com/mcp`, the client requests `https://mcp.example.com/.well-known/oauth-protected-resource/mcp`, and when it does not exist, falls back to `https://mcp.example.com/.well-known/oauth-protected-resource`.

To serve the document from KrakenD, add a [wildcard endpoint](https://www.krakend.io/docs/enterprise/endpoints/wildcard/) with a `backend/static-filesystem` backend to the `endpoints` list of the previous example:

```json
{
  "endpoint": "/.well-known/*",
  "method": "GET",
  "output_encoding": "no-op",
  "backend": [
    {
      "url_pattern": "/",
      "host": ["http://ignore"],
      "extra_config": {
        "backend/static-filesystem": {
          "path": "/etc/krakend/well_known"
        }
      }
    }
  ]
}
```

Then save the metadata document in the file `/etc/krakend/well_known/oauth-protected-resource/mcp`. The path of the file under the `path` directory matches the path of the request after `/.well-known/`, so a single endpoint serves the metadata of all your MCP servers. Its content looks like this:

```json
{
  "resource": "https://mcp.example.com/mcp",
  "authorization_servers": ["https://idp.example.com/realms/krakend"],
  "bearer_methods_supported": ["header"],
  "scopes_supported": ["openid", "roles"]
}
```

The `resource` is the public URL of your MCP endpoint and must match the `audience` you validate. The `authorization_servers` lists the issuers the client can use to get a token, and the client discovers their login and token endpoints from their own metadata. The `scopes_supported` tells the client which scopes to request during the login.

## MCP Tool Filtering by Audience

The **tool filtering** restricts the tools an MCP server exposes according to the audience of each request. Instead of declaring a separate MCP server for every type of consumer, you declare one server with all its tools, tag each tool with the `audiences` allowed to use it, and tell KrakenD where to read the audience of the request. Use it when the same MCP server serves different profiles, such as administrators, support agents, or developers, and each one must see only the tools that belong to them.

KrakenD applies the filter to the two MCP methods that deal with tools:

- `tools/list` omits the tools that do not match the request audience, so the AI agent never learns they exist.
- `tools/call` rejects calls to the tools that do not match, even when the client knows their name.

Read the audience from a trusted source

KrakenD trusts the audience values it reads from the request. If the client sets the header or the path param freely, it can choose its own audience and unlock any tool. Make sure the audience comes from a source you control, such as a header set by your authentication layer, and never from unverified client input.

To enable the filtering, add `tool_audience_source` to the server declaration and `audiences` to each tool. For example, the following configuration declares a server with three tools for different audiences, reading the audience from the `X-Role` header:

```json
{
  "$schema": "https://www.krakend.io/schema/v3.0/krakend.json",
  "version": 4,
  "extra_config": {
    "ai/mcp": {
      "servers": [
        {
          "name": "store-tools",
          "title": "Store tools",
          "version": "1.0.0",
          "instructions": "Provides tools to check the status of the store and manage orders",
          "json_response": true,
          "tool_audience_source": {
            "header_name": "X-Role",
            "on_absent_value": "deny"
          },
          "tools": [
            {
              "name": "list-orders",
              "title": "List orders",
              "description": "Lists the latest orders of the store",
              "audiences": ["support", "admin"],
              "workflow": {
                "endpoint": "/__mcp/list-orders",
                "backend": [
                  {
                    "host": ["https://api.example.com"],
                    "url_pattern": "/orders"
                  }
                ]
              }
            },
            {
              "name": "refund-order",
              "title": "Refund order",
              "description": "Refunds the last order of the store",
              "audiences": ["admin"],
              "workflow": {
                "endpoint": "/__mcp/refund-order",
                "backend": [
                  {
                    "host": ["https://api.example.com"],
                    "url_pattern": "/orders/last/refund",
                    "method": "POST"
                  }
                ]
              }
            },
            {
              "name": "store-status",
              "title": "Store status",
              "description": "Returns the current status of the store",
              "audiences": ["*"],
              "workflow": {
                "endpoint": "/__mcp/store-status",
                "backend": [
                  {
                    "host": ["https://api.example.com"],
                    "url_pattern": "/status"
                  }
                ]
              }
            }
          ]
        }
      ]
    }
  },
  "endpoints": [
    {
      "endpoint": "/mcp",
      "method": "POST",
      "timeout": "10s",
      "backend": [
        {
          "url_pattern": "/ignore",
          "host": ["ignore"]
        }
      ],
      "extra_config": {
        "ai/mcp": {
          "server_name": "store-tools"
        }
      }
    }
  ]
}
```

KrakenD reads the `X-Role` header of every request and exposes a tool when any of the header values matches an entry in its `audiences`. The header accepts several values, either repeated or separated by commas, so a single request can carry more than one audience. The `*` entry in `store-status` matches any audience, which makes the tool available to every request that carries one.

### Audience in the Path

You can read the audience from a path param of the endpoint instead of a header. Set `param_name` to the name of the param, without curly braces, and declare it in the endpoint URL. The param accepts several values separated by commas.

For instance, the following snippet replaces the `tool_audience_source` of the previous example:

```json
{
  "tool_audience_source": {
    "param_name": "audience",
    "on_absent_value": "deny"
  }
}
```

And the endpoint that serves as the entrypoint declares the `{audience}` param:

```json
{
  "endpoint": "/mcp/{audience}",
  "method": "POST",
  "timeout": "10s",
  "backend": [
    {
      "url_pattern": "/ignore",
      "host": ["ignore"]
    }
  ],
  "extra_config": {
    "ai/mcp": {
      "server_name": "store-tools"
    }
  }
}
```

An MCP client connecting to `/mcp/support` gets the tools of the `support` audience, and one connecting to `/mcp/support,admin` gets the tools of both. This approach is useful when the MCP client cannot send custom headers, as you can hand each consumer a different URL.

When you set both `header_name` and `param_name`, KrakenD merges the values of the two sources and exposes the tools that match any of them.

### Behavior When the Audience Is Absent

The `on_absent_value` field decides what happens when the request carries no audience, because the header or the param is missing or empty:

- `deny` (default): KrakenD lists no tools and rejects every tool call. Choose it when every consumer must identify itself, as an unidentified request gets no access at all.
- `allow`: KrakenD lists and accepts calls to all the tools of the server. Choose it when the filtering only narrows down the tools for known audiences, and anonymous consumers can use everything.

Mind that `allow` exposes every tool, including those restricted to specific audiences. If a tool is sensitive, keep the default `deny`.
